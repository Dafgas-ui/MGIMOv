# MGIMOv RC4 — локальная подготовка единого выпуска

Это инструкция для отдельного синтетического стенда и будущей ручной операции
после разрешения пользователя. Она НЕ подтверждает Linux/VPS, не разрешает
публикацию, установку компонентов, cron или изменение рабочей SQLite.
Код P1 зафиксирован в ea4abbca210387e4137d95c5e5f212497b332aaf.
Эта редакция документации пока незакоммичена и требует отдельной проверки.

## 1. Что входит в выпуск

Исходники приложения, 24 SQL-миграции, обычные и браузерные тесты, requirements,
constraints, README и RELEASE. Сборщик package_rc экспортирует рабочее дерево,
включая подходящие untracked-файлы: один base_head не доказывает чистоту сборки.
Перед будущей упаковкой требуются согласованный commit, пустой индекс, чистый
status и сверка манифеста каждого файла с согласованным состоянием. После
упаковки нужны проверка ZIP, SHA-256 и приёмка именно этого артефакта.
Сейчас архив не создавался. Скрипт упаковки не менялся.

SQLite, DPAPI, .env, ключи, сертификаты, установленные зависимости, .tmp,
логи, traces и скриншоты не входят в Git/ZIP. Каталог docs по умолчанию
не упаковывается, поэтому критическая процедура содержится в этом файле.
Переход приложения на новую версию НЕ означает переноса пользователей:
отдельно выбирается миграция прежней БД или новая синтетическая демобаза.
Нельзя молча заменить БД, содержащую действия демонстрационных пользователей.

## 2. Запуск и миграции

Локальный Windows-запуск и приватный checkout описаны в README. Для нового
демо используйте seed_contest_demo, который сам создаёт новую SQLite и применяет
все миграции. Не выполнять init перед ним. Не смешивать seed_mvp_demo (старый
набор пяти аккаунтов), seed_attestations (20), seed_contest_demo (20, но известны
пароли только s01/s02/t01) и отдельные seed_schedule/seed_academics.
Сначала выбрать требуемые сценарии, затем один новый экземпляр и его доступы.

Текущая цепочка: 0001_initial … 0014_legacy_attempt_history …
0015_coursework_foundation … 0020_coursework_files, 0021_coursework_brs_sources,
0022_coursework_brs_authorization, 0023_coursework_brs_server_audit,
0024_attendance, 0025_room_availability. Всего 25 SQL-файлов. Миграция 0023 отменяет ненадёжную функцию
авторизации 0022; гарантия публикации — серверная авторизация, транзакция,
обязательный аудит и права ОС. Произвольный клиент с правом записи SQLite
не входит в эту границу защиты. Применять всю цепочку по порядку.

Startup не создаёт схему. Команды выполняются из соответствующей версии
проекта, с явной БД внутри её физического каталога. Примеры ниже — Linux-стенд;
на Windows заменить .venv/bin/python на .venv/Scripts/python.exe.

```bash
.venv/bin/python -B -m backend.migrations status --db "$candidate_db"
.venv/bin/python -B -m backend.migrations apply --db "$candidate_db" --backup "$new_migration_backup"
.venv/bin/python -B -m backend.commands.diagnose --db "$candidate_db"
```

Оба файла должны быть внутри кандидатного checkout; имя backup новое.
init — только для новой пустой базы, apply — для существующей и с новым backup.
Перед apply необходим отдельный проверенный снимок и сохранённая старая пара.
При ошибке/неизвестной схеме/несовпадении checksum остановиться, не редактировать
историю миграций и не запускать seed поверх базы. Ожидается 25 applied и 0 pending.
Прямое применение 0015–0025 допустимо ТОЛЬКО при статусе managed и подтверждённой
истории ровно 0001–0014: порядок, идентификаторы и checksum должны совпадать
с ожидаемой цепочкой. Проверить это на кандидатной копии до apply. При legacy,
неизвестном состоянии, повреждённой истории или любом несоответствии — STOP.
CLI предоставляет только init/status/apply; команды baseline у него нет.
Не имитировать baseline через init, SQL или правку истории. Дальнейшие действия
требуют отдельного решения после диагностики. Фактическая серверная версия
НЕ проверена и должна быть установлена перед операцией.

## 3. Linux: права и transport до любого открытия трафика

Требуется отдельный непривилегированный пользователь приложения, например mgimov.
Код, .venv, конфигурация службы и переключающий симлинк принадлежат оператору;
приложение не может переписать код или заменить data через права родителя.
Каталог data — 0700, SQLite — 0600, владелец — пользователь приложения.
UMask=0077; существующие файлы проверить отдельно. Проверить все родители,
ACL, отсутствие перенаправлений, фактические WAL/SHM/journal при записи.
Права проверяются также после restore и перезапуска. Nginx и другой
непривилегированный пользователь не должны читать/изменять SQLite, вложения
в ней, backup, staging и карантин. У них нет прав удалить data через родителя.
Это проверяется на тестовых файлах от имени разных пользователей, не на production.

Фрагмент systemd для стенда, не готовый установленный unit:

```ini
[Service]
User=mgimov
Group=mgimov
UMask=0077
NoNewPrivileges=yes
PrivateTmp=yes
ProtectSystem=strict
WorkingDirectory=/opt/mgimov-lab/release-a
Environment=MGIMOV_DB_PATH=/opt/mgimov-lab/release-a/data/lab.sqlite3
Environment=MGIMOV_ORIGIN=http://127.0.0.1:18031
ReadWritePaths=/opt/mgimov-lab/release-a/data
ExecStart=/opt/mgimov-lab/release-a/.venv/bin/python -B -m uvicorn backend.app:app --host 127.0.0.1 --port 18031 --no-proxy-headers
```

Пути относятся исключительно к отдельному стенду. Python 3.13 проверен на
Windows; наличие подходящего Python и SQLite на Ubuntu 24.04 нужно проверить.
Ничего не устанавливать по этой инструкции без разрешения. Для job backup
нужен отдельный проверенный доступ к backup-каталогу: ReadWritePaths выше
разрешает запись только в data, а не автоматически в daily backups.

Loopback HTTP и публичный HTTPS — РАЗНЫЕ режимы. Для HTTPS установить точный
MGIMOV_ORIGIN=https://<согласованный-хост> и доверять forwarded headers только
известному reverse proxy. Для единственного Nginx на loopback допустимы
--proxy-headers --forwarded-allow-ips=127.0.0.1 вместо --no-proxy-headers.
Никогда не использовать доверие ко всем адресам. Backend слушает только loopback.
Nginx должен передавать Host и выставлять X-Forwarded-Proto из собственного TLS,
а клиентские forwarded-значения не должны становиться доверенными.
Обслуживать приложение через согласованный proxy; не публиковать весь каталог
релиза через root/alias. Проверить отсутствие HTTP-доступа к data/.tmp/backend,
SQLite, WAL/SHM, backup и секретам. Не копировать настройки из примера вслепую.

Проверить доверенную цепочку сертификата, hostname, сроки и продление; запрос
с отключённой проверкой TLS не является PASS. Проверить Host/Origin, вход
Student/Staff, logout, защиту CSRF и cookies: Secure + __Host- при HTTPS,
HttpOnly для сессии, SameSite=Strict, Path=/. Не сохранять значения cookies
в отчётах. Health 200 сам по себе не доказывает работоспособность входа:
неправильный ASGI scheme может приводить к отказу защищённых API.

## 4. Backup, restore, сессии и rollback

Перед остановкой можно сделать предварительный online-снимок SQLite Backup API.
Для финального снимка остановить конкретную службу и других согласованных
писателей (job backup/миграции/локальные команды), дождаться выхода процессов.
Не использовать pkill. На тестовой БД проверить отсутствие писателей через
BEGIN EXCLUSIVE с timeout=0 и последующий rollback; для WAL проверить checkpoint
busy=0. При занятости — остановиться; не удалять WAL/SHM вручную.
Финальный backup должен включать последние подтверждённые данные до остановки.
Старые файлы не копировать обычным cp при живых писателях или несведённом WAL.

Дневной backup CLI текущего релиза требует схему именно текущего релиза,
полный integrity/foreign_key/schema/checksum контроль. Старую БД 0014 нельзя
считать несовместимой только потому, что текущий CLI ожидает 0025, и нельзя
обходить эту проверку. Для предмиграционного снимка 0014 нужен совместимый
SQLite Backup API и проверка прежней версией; мигратор дополнительно создаёт
свой новый backup перед DDL. Возможность реального RC3.1 rollback должна
репетироваться отдельно: в RC3.1 ещё нет нового restore CLI.

На Linux backup CLI автоматически включает production-ограничения: источник
вне .tmp, явные совпадающие абсолютные --db и MGIMOV_DB_PATH, каталог строго
/opt/mgimov/backups/daily. Этот путь в локальной репетиции создаётся ТОЛЬКО
в одноразовой VM/дистрибутиве без production, не на FirstVDS.
Каталог и родители проверены, daily 0700, файлы 0600, нет root/alias публикации.

```bash
.venv/bin/python -B -m backend.commands.backup_database --production --db "$MGIMOV_DB_PATH" --directory /opt/mgimov/backups/daily --keep-successful 7 --max-bytes 1073741824
.venv/bin/python -B -m backend.commands.check_backup --directory /opt/mgimov/backups/daily --date "$backup_day"
.venv/bin/python -B -m backend.commands.restore_database --backup-directory /opt/mgimov/backups/daily --date "$backup_day" --output "$restore_file" --confirm-test-restore
.venv/bin/python -B -m backend.commands.diagnose --db "$restore_file"
```

MGIMOV_DB_PATH — подтверждённый абсолютный путь в data стенда, backup_day —
UTC-дата реально опубликованного комплекта. restore_file — новое имя строго
в приватной .tmp соответствующего тестового проекта, вне backup. Команда
не перезаписывает файл или sidecar, требует hard link и совместимость всех
миграций. Нельзя восстановить snapshot 0014 этим CLI под кодом 0025.
Не переименовывать staging/quarantine в опубликованный комплект вручную.
При нехватке квоты сохранять исправные копии; не удалять последнюю пригодную.
Хранится минимум 7 успешных дней, а не 7 календарных суток с пропусками.
Cron и проверка свежести — отдельные задания, включать только после проверки
реальной доставки MAILTO/локального канала. Logger не равен доставке сообщения.
В этой операции расписание не включено; Linux/cron/MAILTO NOT VERIFIED.

### Отзыв сессий после восстановления — обязательная политика

Только после проверки restore в НОВОМ файле, до первого запуска приложения
на нём, остановить все его писатели. Восстановленные сессии отозвать все.
Это предотвращает возврат токенов, отозванных после момента снимка.
Цель — именно абсолютный путь `$restore_file`, переданный в `restore_database
--output "$restore_file"`, а не исходная SQLite, выбранная по умолчанию.
До открытия SQL-клиента оператор сверяет этот путь с результатом restore:
файл существует, является новой проверенной копией внутри приватной .tmp
тестового проекта, не является симлинком и не совпадает с исходной БД или
backup ни по каноническому пути, ни как hard link на тот же файл. При сомнении — STOP.
SQL-клиент открывается явно на `$restore_file` (не на MGIMOV_DB_PATH и не на
автоматически выбранной базе); его фактический подключённый файл проверяется
через `PRAGMA database_list` и должен совпасть с проверенным путём. До этой
сверки запуск следующей команды ЗАПРЕЩЁН. Она массово отзывает все активные
сессии целевой копии; запуск на исходной БД отключит её пользователей.
Оператор выполняет транзакцию ТОЛЬКО в этом проверенном подключении:

```sql
BEGIN IMMEDIATE; UPDATE sessions SET revoked_at=CAST(strftime('%s','now') AS INTEGER) WHERE revoked_at IS NULL; COMMIT;
```

Это инструкция, не автоматически выполняемая функция restore CLI. Очистка
истёкших сессий cleanup_sessions не заменяет отзыв всех восстановленных.
Проверить integrity/FK повторно, старый тестовый cookie должен дать 401,
новый login Student/Staff — успех. SHA восстановленной БД после отзыва
закономерно меняется: сравнивать академические контрольные данные, а исходный
backup и исходную БД проверять на неизменность SHA. Карантин/исходники не изменять.
Проверить также блокировки аккаунтов и изменения полномочий после точки снимка:
rollback возвращает старое состояние, это требует решения оператора.

### Ручной выпуск и аварийный откат — только после отдельного разрешения

1. Зафиксировать прежний физический каталог кода, SQLite, миграции, настройки,
   владельцев, контрольные значения, время точки восстановления. Сохранить пару.
2. Проверить отдельный кандидат и миграцию на копии данных. Никакого seed на рабочей БД.
3. В согласованное окно закрыть запись, остановить точную службу/писателей,
   сделать и проверить финальный снимок. Если шаг неуспешен — прежняя пара остаётся.
4. Создать согласованную кандидатную копию SQLite, применить миграции с новым
   backup, diagnose, права. Не менять старую БД. При ошибке не переключать.
5. Переключать каталог кода и MGIMOV_DB_PATH как одну пару. Settings запрещает
   БД за пределами физического ROOT. Простого переключения симлинка недостаточно,
   если в unit остался старый абсолютный путь БД/WorkingDirectory/ExecStart.
6. Запустить точную службу. Проверить health, TLS, настоящий login обеих ролей,
   чужие данные 403/404, расписание, БРС, зачётку, Coursework/вложения,
   посещаемость и сроки. До успешной проверки не открывать общий доступ.
7. При ошибке остановить кандидат и писателей; сохранить его БД/WAL/SHM для
   разбора. В старом физическом релизе восстановить НОВУЮ копию старой схемы
   из финального снимка совместимым инструментом, проверить данные и права,
   отозвать восстановленные сессии. Указать старый код + эту БД и запустить.
8. Проверить health и login, контрольные данные, отсутствие новых ошибок.
   SQL downgrade не выполнять. Повторный rollback — снова в новый файл.
   Записи после снимка могут быть утрачены; не обещать нулевую потерю данных.

## 5. План локальной репетиции (пока НЕ выполнен на Linux)

1. Выделить изолированную Ubuntu 24.04 с native Linux filesystem, без production,
   mounts VPS, ключей и реальных данных. Проверить Python/SQLite, hard link,
   flock, loopback, владельцев. Для systemd нужен полноценный systemd-стенд;
   обычный контейнер покрывает CLI/HTTP, но не доказывает unit/Nginx/TLS.
   Не использовать /mnt/c или общую доступную другим папку как приватный storage.
2. Из чистого согласованного checkout создать новую seed_contest_demo базу
   с текущими датами. Записать только логины/роли и контрольные агрегаты:
   расписание, опубликованные БРС, официальные оценки, версии Coursework,
   попытки/проверки/вложения, посещаемость, долги. Пароли скрыто, не в отчёт.
3. После остановки seed/test-сервера сформировать согласованную копию через
   SQLite Backup API из полученного DEMO_DB в новый data/lab.sqlite3 внутри
   того же проекта (не обычным копированием живого WAL). Проверить diagnose,
   затем использовать этот абсолютный путь как MGIMOV_DB_PATH для Linux CLI.
4. Запустить loopback Uvicorn, проверить реальный Student/Staff login и контрольные
   данные; завершить только его процесс. Создать и проверить дневной комплект
   командами раздела 4. Проверить SHA, integrity_check, foreign_key_check,
   schema/checksums и пустой pending. Сохранить исходные SHA и контрольные значения.
5. В отдельной кандидатной копии проверить apply: заполненный синтетический
   baseline 0014 обновляется до 0025, сохраняет данные, повторный apply — no-op.
   Подготовка baseline должна содержать только миграции 0001–0014, не удаления
   таблиц из готовой 0025. Для начального теста используйте существующие
   миграционные тестовые фикстуры, не рабочую базу. Дополнительно имитировать
   ошибочную новую миграцию и проверить атомарный rollback на кандидатной копии.
6. Выполнить restore в новый приватный файл, до любых записей сверить SHA,
   затем отозвать сессии и повторно проверить целостность. Запустить FastAPI
   с явным MGIMOV_DB_PATH на эту копию и проверить login и контрольные данные,
   включая точное содержимое синтетического TXT-вложения и отказ чужому студенту.
7. В ещё одной копии добавить НОВУЮ тестовую миграцию после последней (сейчас
   0026_rehearsal), оставить её неприменённой и получить health 503. Не изменять
   исходный checkout. Остановить процесс; проверить освобождение БД и sidecar.
8. Restore предыдущего комплекта повторить в два новых файла под прежним кодом.
   Каждый раз: отзыв сессий, права, health/login и сравнение академических данных.
   Сверить неизменность исходной БД и backup. Записать потерю изменений кандидата
   после снимка как ожидаемое свойство rollback, сохранить кандидат для разбора.
9. На синтетике проверить ошибку SHA, существующий output, отказ прав, удержание
   writer lock, stale WAL/SHM, конкурентный backup, SIGTERM/SIGKILL собственного
   job, восстановление staging. Реальный ENOSPC — только в отдельно разрешённой
   ограниченной файловой системе; не заполнять системный диск.
10. Измерить размер SQLite и WAL, свободное место, RSS/CPU и длительность backup.
    Нужны 7 комплектов + место для нового до ротации, исходная и восстановленная
    копии, migration backup, ручные копии и карантин. Пример квоты 1 GiB выше
    НЕ является расчётом ёмкости VPS. verified_backup сравнивает полные iterdump
    в памяти, поэтому загрузка TXT/MD может заметно увеличить пик RAM.
11. Только после CLI/HTTP перейти к отдельной приёмке systemd, пользователей,
    Nginx/TLS и уведомлений. Успех Windows или кода-примера не равен Linux PASS.

На Windows существующая автоматическая репетиция —
python -B -m unittest tests.test_recovery_rehearsal -v — из приватного checkout
с тестовыми зависимостями. Она запускает реальные CLI/Uvicorn и два rollback,
но не реализует новую операторскую политику отзыва всех восстановленных сессий.
Эта политика требует отдельной проверки до боевого restore. Тест на Linux
помечен SKIP: используйте описанный Linux-план, а не засчитывайте SKIP за PASS.
