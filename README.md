# Цифровой деканат будущего — V6

Конкурсный концепт. Неофициальный сервис. Все данные вымышлены.

Самостоятельное приложение: Python 3.13/FastAPI, SQLite, HTML/CSS/JavaScript ES modules.
Реализованы вход, серверные сессии, роли student/staff и собственные профили.
Реализованы групповое расписание и история изменений. Реализованы личная зачётка, экзамены, задолженности и прогресс. Реализованы электронные заявки и ограниченная очередь сотрудника. Уведомления ещё не реализованы. Конкурсный MVP не готов.

## Подготовка изолированной демонстрационной среды (PowerShell)

Команды выполняются из корня проекта. Новая база должна иметь новый путь;
существующие файлы не перезаписываются. Рабочую data/deanery.sqlite3 V2 не мигрировать
без отдельного решения. Для V6 по умолчанию старой базы недостаточно: health=503.

```powershell
# Только если окружение ещё не подготовлено:
python -m venv .venv
python -m pip --python .venv install -r requirements.txt

$env:MGIMOV_DB_PATH = '.tmp/demo-v6.sqlite3'
$env:MGIMOV_ORIGIN = 'http://127.0.0.1:8010'
& .\.venv\Scripts\python.exe -B -m backend.migrations init
& .\.venv\Scripts\python.exe -B -m backend.commands.seed_demo --db .tmp/demo-v6.sqlite3 --confirm-demo
& .\.venv\Scripts\python.exe -B -m backend.commands.seed_schedule --db .tmp/demo-v6.sqlite3 --confirm-demo
& .\.venv\Scripts\python.exe -B -m backend.commands.seed_academics --db .tmp/demo-v6.sqlite3 --confirm-demo
& .\.venv\Scripts\python.exe -B -m backend.commands.seed_requests --db .tmp/demo-v6.sqlite3 --confirm-demo
& .\.venv\Scripts\python.exe -B -m uvicorn backend.app:app --host 127.0.0.1 --port 8010 --no-proxy-headers
```

Seed запускается в интерактивном терминале: оператор скрыто вводит и повторяет
три новых пароля (15–128 символов). Создаются student_a, student_b, staff_demo.
Пароли не выводятся и не записываются в документы; в базе только Argon2id.
Передать тестовые реквизиты пользователю отдельно, вне Git и публичных логов.
Команда отказывается работать с базой по умолчанию, с существующими users,
без явного --db/--confirm-demo или без интерактивного ввода. Startup не создаёт
аккаунты и не выполняет миграции. Отдельного HTTP seed/registration endpoint нет.

Открыть http://127.0.0.1:8010/; завершить сервер Ctrl+C. Не использовать file://.
Студенты имеют разные вымышленные профили и группы; сотрудник видит только
своё ФИО/должность. Общего каталога профилей нет. Вход по Enter, выход и повторный
вход поддерживаются. Профиль при обновлении запрашивается по серверной сессии.

## Конфигурация и безопасность

MGIMOV_DB_PATH — путь SQLite внутри проекта; MGIMOV_ORIGIN — точный origin без
пути, в нижнем регистре. .env не читается. Для другого локального порта измените
и origin, и --port. HTTP разрешён только на loopback. При публичном HTTPS origin
должен быть https://…: Secure и __Host- cookies включаются автоматически.
Публичное развёртывание в этом задании не выполняется; схему транспорта и доверие
к reverse proxy необходимо настраивать отдельно, не доверять произвольным forwarded headers.
Срок сессии по умолчанию 8 часов. Нет режима отключения авторизации.

API: GET /api/v1/auth/csrf, POST /api/v1/auth/login,
GET /api/v1/auth/me, GET /api/v1/me/profile, POST /api/v1/auth/logout.
Вход требует pre-login CSRF token из bootstrap и cookie + точный Origin;
выход требует CSRF header/cookie, связанные с серверной сессией.
Лимиты входа сохраняются в SQLite в окне 60 секунд: пара source/login — 5,
источник — 30 неудачных/незавершённых резервирований. Нет общего запрета по логину
для всех адресов и нет общего 15-минутного бюджета приложения. Успех возвращает
только свою резервацию. Повторный 429 не пишет в SQLite и не запускает Argon2.
Две проверки одновременно и одна на логин в одном процессе; перегрузка даёт 503.
Общий NAT и распределённые источники всё ещё требуют защиты proxy.
Сессионные токены случайны; в базе только SHA-256-хеши session/CSRF.
Профили выбираются сервером по сессии, query/GET body не выбирают владельца.
Frontend не хранит профиль/пароль/сессию в localStorage. Cookies HttpOnly для
сессии, SameSite=Strict, Path=/; CSRF-cookie доступна JS перед выходом.

## Расписание V4

После отдельного создания демобазы и пользователей выполните seed_schedule (в примере выше).
По умолчанию создаётся текущая московская неделя; для повторяемой даты можно добавить
`--week-of 2026-11-04`. Повторный seed не перезаписывает существующее расписание.
Для перехода с существующей V3-демобазы сначала требуется отдельно разрешённое apply
с новым backup, затем seed_schedule. Рабочая data/deanery.sqlite3 этим этапом не менялась.

GET `/api/v1/me/schedule?view=today&date=2026-11-04` — выбранный день;
`view=week` — неделя с понедельника. Без date сервер использует сегодня в Europe/Moscow.
Разрешённый диапазон выбора дат: 1900–2100; API не принимает group_id/user_id.
Студент получает только группу своей серверной сессии, staff не получает расписание
произвольных групп. Нет endpoint публичного редактирования.

Демонстрация: две разные группы/дисциплины/время занятий. Группа А содержит отмену,
перенос, замену аудитории и преподавателя; изменения видны вместе с «было/стало».
На прежнем дне переноса остаётся неактивная карточка с новой датой; это не второе
занятие и не занятость комнаты. Источник реальных интервалов — только lessons
с status=scheduled, не UI-маркеры из истории.

Изменить отдельное занятие можно доверенной локальной командой с явной базой,
версией и причиной (примеры относятся только к созданной демобазе):

```powershell
& .\.venv\Scripts\python.exe -B -m backend.commands.change_lesson --db .tmp/demo-v6.sqlite3 --lesson demo-a-4 --version 1 --reason "Демонстрационная отмена" --status cancelled --confirm-change
```

Перенос: `--date YYYY-MM-DD --start-minute 660 --end-minute 750`;
замена: `--room-id demo-r3` или `--teacher-id demo-t2`. При неверной версии/ссылке
запись отклоняется, занятие и история меняются атомарно. Это не веб-кабинет сотрудника.
Серии повторений, бронирование и поиск свободных комнат не реализованы.
Модель корпусов/аудиторий/capacity/equipment/интервалов подготовлена для будущего поиска.


## Успеваемость V5

На новой демобазе сначала seed_demo, затем seed_schedule и seed_academics.
Последний создаёт два семестра и персональные назначения, разделяет вымышленную
программу группы Б (только demo-b) с программой А; существующие оценки не перезаписывает.
`--as-of YYYY-MM-DD` предназначен для воспроизводимой демосреды; без него используется
сегодня по Москве. Для демонстрации в другую дату лучше создать новую временную базу.
Существующая V4-демобаза требует явного apply с новым backup перед seed_academics.
Старые миграции не менялись, рабочая SQLite не используется.

Защищённые GET без query-параметров:

- `/api/v1/me/gradebook` — семестры, назначения, попытки, текущий прогресс,
  предстоящие испытания и задолженности одним согласованным снимком;
- `/api/v1/me/exams` — все свои назначенные экзамены/зачёты, включая прошедшие;
- `/api/v1/me/debts` — подтверждённые задолженности обязательных испытаний всех семестров;
- `/api/v1/me/progress` — текущий учебный период и его прогресс.

В MVP «текущая сессия» — назначения семестра, содержащего сегодняшнюю московскую дату.
Успех: экзамен/дифференцированный зачёт 3–5, зачёт — pass («Зачтено»).
Оценка 2 / fail и явная неявка — задолженность. Без попытки задолженность возникает
только при status=completed и явном deadline_on раньше сегодня; сам день срока ещё
не просрочен. Будущие/непроведённые/неизвестные испытания и отсутствующая оценка
различаются. Нет текущих обязательных назначений — «Нет данных», percent=null.
Необязательные и отменённые испытания исключены из знаменателя.

Прогресс = успешно завершённые / все обязательные неотменённые назначения текущего
семестра ×100, округление до целого. Предстоящие, долги и ожидающие уточнения вместе
с завершёнными образуют полный счётчик. Исторические долги показываются отдельно,
не добавляются в знаменатель текущей сессии. Каждое назначение считается один раз.
Последняя по номеру попытка определяет результат; новая попытка после успеха запрещена.
Неуспех → успешная пересдача снимает долг, сохраняя обе попытки.

Локальная запись результата для уже завершённого испытания отдельной демобазы:

```powershell
& .\.venv\Scripts\python.exe -B -m backend.commands.record_result --db .tmp/demo-v6.sqlite3 --assignment academic-b-0 --expected-attempts 1 --outcome graded --grade 4 --performed-on 2026-11-04 --confirm-demo
```

Дату примера заменить на фактическую дату попытки не раньше назначенного испытания
и не позже сегодня. Для зачёта --outcome pass/fail без --grade; для неявки absent.
Команда добавляет попытку атомарно, проверяет тип контроля, даты, число прошлых попыток
и завершённость мероприятия. Исправление успешной оценки и управление датами/статусами
мероприятий не входят в этот CLI; произвольной перезаписи истории нет.
Это инструмент доверенного локального оператора, не веб-права сотрудника.
Публичных POST/PUT/PATCH/DELETE оценок нет. Данные не сохраняются в localStorage.


## Электронные заявки V6

На отдельной демобазе после seed_demo выполните seed_requests (см. полный запуск выше).
Seed создаёт четыре вымышленных обращения: submitted/processing/approved/rejected,
и явное право staff_demo обрабатывать только факультет demo-f. Повторный seed не
перезаписывает заявки или права. Рабочая SQLite не менялась. Для существующей V5-демобазы
сначала явный apply с новым backup; старые миграции не редактировать.

В кабинете ссылка «Перейти к обращениям» открывает раздел без прокрутки всей зачётки.
Студент: «Создать заявку» → тип → назначение справки (кроме свободного обращения)
и комментарий → «Отправить заявку». Доступны список, детали, статус, история и
комментарии сотрудника. Новую заявку можно отменить только до начала обработки.
Черновиков нет: несданная форма остаётся лишь в текущей вкладке при проверке того же
аккаунта; при выходе/смене/недействительной сессии очищается. Перезагрузка её не сохраняет.
Сотрудник: очередь доступных факультетов → детали → действие и обязательный комментарий.
Запрос уточнения и редактирование текста после отправки не входят в MVP.
Одобрение не выпускает официальную справку, подписи, печати или PDF.

Статусы и переходы:

| Роль | Из | В | Условие |
|---|---|---|---|
| Студент | новая отправка | submitted | Владелец/факультет из серверного профиля |
| Студент | submitted | cancelled | Только своя заявка |
| Сотрудник | submitted | processing | Явный доступ к факультету заявки |
| Сотрудник | processing | approved / rejected | Обязательный комментарий / причина |

approved/rejected/cancelled — терминальные, возврата в работу нет. Каждое изменение
проверяет version, увеличивает её на 1 и атомарно добавляет автора/роль/время/комментарий
в append-only историю. При устаревшей версии — 409, нужно обновить детали.

API (все ответы no-store):

- GET/POST `/api/v1/me/requests` — собственный список / создание;
- GET `/api/v1/me/requests/{id}` — свои детали;
- POST `/api/v1/me/requests/{id}/cancel` — `{version, comment?}`;
- GET `/api/v1/staff/requests` и `/{id}` — очередь / детали в явной области доступа;
- POST `/api/v1/staff/requests/{id}/decision` — `{version, action, comment}`.

Списки принимают только одиночный offset (по умолчанию 0), по 20 записей,
возвращают next_offset; интерфейс содержит переходы страниц. Детали/POST query не принимают.
Создание: `{type, purpose, message, request_key}`. Типы study_certificate,
general_certificate, appeal. purpose до 200 символов, обязателен для справки и пуст
для appeal; message 1–2000, комментарий решения 1–1000; общий body до 8192 байт.
Пробельные обязательные поля и запрещённые управляющие символы отклоняются.

request_key — криптографически случайные 32 hex-символа для одной отправки.
До POST в sessionStorage этой вкладки сохраняются только ключ, тип формы, срок
действия (24 часа) и SHA-256 тег привязки к аккаунту с этим случайным ключом.
Текст, UUID пользователя, имена, пароли, cookies и содержимое форм туда не попадают. Повтор того же нормализованного содержимого с тем же ключом вернёт
тот же объект (200 вместо 201), даже после изменения его статуса. Другое содержимое
с тем же ключом — 409. При неопределённом результате сначала проверьте список. После reload и
подтверждения того же аккаунта интерфейс предложит повторить те же поля с прежним
ключом. Текст надо ввести снова. Изменённое содержимое с ключом уже сохранённой
заявки даёт 409, не новую запись. Для отдельной осознанной заявки есть кнопка
«Начать отдельную заявку»; после подтверждённой отправки следующая тоже получает новый ключ.
Logout удаляет технический маркер, другой аккаунт его не восстанавливает. При
истечении сессии маркер не даёт доступа: сначала повторный вход того же пользователя.
Закрытие вкладки обычно очищает sessionStorage; восстановление вкладок зависит от
браузера. При отсутствии/истечении/повреждении маркера сначала проверьте список.
При заблокированном хранилище отправка приостанавливается, новый ключ молча не отправляется.
Двойной клик блокируется на клиенте, уникальность и атомарность обеспечены сервером.
Лимит создания на студента: 5 за скользящие 600 секунд и 20 за 86400 секунд;
отменённые учитываются, повторы по ключу квоту не расходуют. Превышение — 429.

Staff не получает автоматические права по одному значению роли. Область задаётся
request_staff_scopes, в демосреде — локальным seed. Отсутствие scope даёт пустую очередь
и 404 для недоступной заявки. Веб-редактора полномочий и универсальной админ-панели нет.
Факультет фиксируется при отправке заявки. Студент всегда читает её по своему server user.id.
POST требует existing session-bound CSRF cookie/header, exact Origin и JSON.


### Исправления AUD-01 / AUD-02

Несданный комментарий сотрудника хранится только в памяти, отдельно для сотрудника
и обращения. Он переживает ручную/фоновую проверку того же входа, обновление деталей,

сохранённый текст можно скопировать из поля только для чтения. Выход, смена аккаунта
и перезагрузка очищают эти комментарии. localStorage не используется.

### UX-01 — переключение вкладок

При обычном скрытии вкладки профиль, учебные данные и обращения скрываются,
административные действия блокируются. Несданный комментарий сотрудника и заполненная
форма заявления сохраняются только в оперативной памяти. После возврата выполняются
GET проверки сессии/профиля и доступа к выбранному обращению. Тот же пользователь
получает свои поля обратно; истёкшая сессия, другая личность/роль или серверный отказ
в доступе к заявке очищают соответствующие черновики. Автоматического решения нет.
Временная ошибка сети оставляет текст скрытым до успешной проверки входа.

Logout и pagehide при уходе/перезагрузке страницы по-прежнему очищают чувствительные
поля. Закрытие вкладки, перезагрузка и выключение устройства не сохраняют текст.
Техническое восстановление ключа отправки AUD-02 остаётся прежним, без сохранения формы.
Пароль входа при скрытии очищается. Редактирования профиля в текущем интерфейсе нет.

В Chrome или Edge откройте **http://127.0.0.1:8030/**. Используйте именно 127.0.0.1,
не localhost: Host/Origin защищённых API должны точно совпадать. Точка входа —
backend/app.py, объект app (factory create_app). Остановить — Ctrl+C в PowerShell.
Для проверки именно MGIMOv: надпись «MGIMO AI Challenge 2026 · V6», заголовок
«Цифровой деканат будущего», предупреждение о вымышленных данных; health по адресу
http://127.0.0.1:8030/api/health возвращает status ok после подготовки схемы.

Если порт занят, не завершайте чужой процесс. Посмотрите
`Get-NetTCPConnection -LocalPort 8030 -State Listen` и выберите свободный 8001:
замените 8030 на 8001 **в MGIMOV_ORIGIN, --port и адресе браузера**, сохранив путь БД.
