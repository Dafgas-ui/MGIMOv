# План технических этапов RC4

## Этапы и владельцы

1. RC4.1. Резервное копирование и восстановление, затем полный сценарий учебной
   работы от назначения до подтверждённой публикации в БРС.
2. RC4.2. Посещаемость, аудитории и каталог услуг. Каталог использует серверную
   маршрутизацию для военной кафедры и практик. Спорт и элективы используют
   транзакционные проверки вместимости и сроков.
3. RC4.3. Остальные согласованные функции, аватары, интеграция дизайна и общий
   регрессионный прогон перед единым ZIP. Полный список 31 функции нужно сверить
   с утверждённым реестром. ИИ остаётся архитектурной задачей.

Sol ведёт backend, миграции, тесты и документы контрактов. Design Lab владеет
frontend и визуальными сценариями. Общие файлы подключаются после handoff.
Приёмка каждого этапа включает обновление копии SQLite, проверку прав,
сохранность истории и проверку с предыдущим интерфейсом.

## Проект контракта учебных работ

Действующие JSON-маршруты защищены серверной сессией. Для записи обязательны
Origin, CSRF и `Content-Type: application/json`.

| Метод и путь | Назначение |
|---|---|
| GET /api/v1/me/coursework | Собственные работы, фильтры по семестру и потоку |
| GET /api/v1/me/coursework/{id} | Карточка с собственными попытками и версиями проверок |
| POST /api/v1/me/coursework/{id}/submissions | Текстовая сдача. Ответ 201 |
| GET /api/v1/staff/coursework | Работы и доступные потоки действующих назначений |
| POST /api/v1/staff/coursework | Создание черновика. Ответ 201 |
| GET /api/v1/staff/coursework/{id} | Карточка и список получателей с версиями |
| GET /api/v1/staff/coursework/{id}/recipients/{course_id} | Попытки и проверки выбранного получателя |
| PATCH /api/v1/staff/coursework/{id} | Частичное редактирование черновика |
| POST /api/v1/staff/coursework/{id}/commands | Публикация, копирование, очная сдача, возврат и проверка |

Списки принимают только `offering_id` и `semester_id` и возвращают `items`.
Staff дополнительно получает `offerings` с `id`, `group_id`, `subject_id`
и `semester_id`, а также `subject_name` и `group_name`. В списках и карточках обеих
ролей эти названия получены из дисциплины учебного плана и группы исходного потока.
Отдельного названия потока в модели нет. `semester_id` возвращается в обоих представлениях.
Карточка возвращает `id`, `offering_id`, `kind`, `title`,
`description`, `due_at`, `created_at`, `mode`, `status`, `version`,
`grading_mode`, `event_code` и `max_points`. Максимум для БРС берётся из
утверждённого плана. Student получает `recipient_version` для команд сдачи.
Student также получает `latest_attempt_no`, `latest_attempt_state` (null,
`submitted`, `reviewed`, `returned`, `retry_allowed`), `has_latest_review`,
`can_submit_text` и `can_resubmit`. Последний флаг означает доступность
повторной **текстовой** сдачи по текущему серверному состоянию. Он учитывает
способ сдачи, исходное зачисление и решение по последней попытке. Запись
повторно проверяет условия, включая версию.

В списке и карточке Staff объект `queue` содержит `recipients` (все получатели),
`submitted` (получатели с хотя бы одной попыткой), `awaiting_review` (последняя
попытка без проверки), `reviewed` и `returned` (включая решение `retry_allowed`).
В деталях Staff получатели содержат `course_id`, `enrollment_id`, `student_id`,
`student_name` из профиля и `version`. История выбранного получателя также
возвращает `student_name`. Имена получателей доступны только через Staff
с подтверждённым назначением. Попытки содержат `number`, `method`, `response`, `submitted_at`,
`late` (0/1). Проверки содержат `attempt_no`, `revision`, `decision`, `points`,
`comment`, `reviewed_at`, `reason`. Время передаётся в секундах Unix.

Создание принимает `offering_id`, `kind`, `title`, `description`, `due_at`,
`mode`, `request_key`. PATCH принимает `expected_version`, `request_key`
и `data` с одним или несколькими полями из `kind`, `title`, `description`,
`due_at`, `mode`. Текстовая сдача принимает `expected_version`, `request_key`,
`response`. Команды Staff принимают `expected_version`, `request_key`,
`action` и `data`. Ключ повтора содержит 16–64 символа A–Z, a–z, 0–9, `_`, `-`.

Черновик принимает поток, название, описание, тип, дедлайн и режим сдачи.
Режим оценивания задаётся при публикации. Команды принимают
ожидаемую версию и ключ повтора. Запись проверки содержит балл, комментарий и
причину для исправления. Успех возвращает идентификатор и версию команды.
Ошибки используют `detail`. Общая защита возвращает 400 для некорректного
Host или дублированных защищённых заголовков, 401 для недействительной сессии,
403 при запрете роли, Origin или CSRF, 404 для недоступного объекта, 409 при
конфликте версии, публикации или попытки, 413 при превышении лимита тела,
415 для неподдерживаемого формата и 422 для недопустимых либо пустых полей.
Недоступная SQLite или схема даёт 503.

Лимит тела — 8192 байта, за исключением POST текстовой сдачи с лимитом
32768 байт. Middleware считает фактически полученные байты до разбора JSON.
Поле `response` допускает до 4000 Unicode-кодовых точек в исходной строке.
Клиенту следует отправлять JSON в UTF-8. Избыточное экранирование, в том числе
суррогатными парами `\uXXXX`, учитывается в лимите тела.

Работа имеет состояния draft и published. Попытка появляется при сдаче;
последняя версия проверки содержит reviewed, returned или retry_allowed.
Просрочка вычисляется по дедлайну, отправка разрешена без штрафа.
Повтор требует возврата или явного разрешения. Копия работы в другом потоке
содержит текст и параметры задания без получателей и результатов.

Student видит свои записи. Преподаватель работает в рамках актуального назначения.
История связывается с постоянным курсом и исходным зачислением. Сводка деканата,
публикация баллов в БРС и PDF остаются отдельными этапами.

Серверные сервисы работают со схемой 0019. Черновик создаётся в потоке с действующим назначением на
весь поток. Опубликованное задание получает список активных зачислений на момент
публикации. Последующий перевод сохраняет чтение истории старой работы и
закрывает новые сдачи по прежнему зачислению. Получатели уже опубликованной
работы автоматически не пересчитываются.

Команды сервиса: `publish` (`grading_mode` и параметры режима), `copy`
(`target_offering_id`, необязательный `due_at`), `submit_text` (`response`),
`record_in_person` (`course_id`), `review` (`course_id`, `attempt_no`,
`decision`, `comment`, необязательный `points` и `reason` для новой версии). Для публикации и копирования
передаётся версия задания. Для сдачи и проверки передаётся версия записи
получателя. Версия задания при копировании сохраняется. Результат команды
содержит `assignment_id`, `version` и при необходимости `copy_id`,
`attempt_no`, `late` или `review_revision`. Повтор ключа с другим телом даёт 409.

Копия получает новый ID и статус draft. Связь с мероприятием выбирается заново
при публикации в целевом потоке, как и режим оценивания. Уникальность действует внутри потока, который
однозначно связан с планом и его учебной позицией. Проверка добавляет версию
`reviewed`, `returned` или `retry_allowed`. Последние два решения разрешают
одну следующую сдачу. Попытка хранит время и отдельный флаг просрочки.

Режимы публикации: `ungraded` — решение и комментарий без балла,
`independent` — локальные целые баллы от 0 до `max_points` (максимум от 1 до 100),
`brs` — обязательный `event_code`, максимум из утверждённого плана.
Опубликованные параметры оценивания заморожены. Для старых вызовов без
`grading_mode` наличие `event_code` определяет режим `brs`, иначе используется
`ungraded`. Оценка может отсутствовать. Ноль является выставленным баллом.

Совпадающий опубликованный результат по получателю, потоку и событию возвращает
409 с полями `detail` и `code: coursework_brs_result_already_published`
без идентификаторов студентов и оценок.
Сверка спорных результатов потребует отдельной команды с полномочиями и аудитом.
Обычная публикация попытки БРС также проверяет привязку к работе в той же
транзакции. Миграция 0018 защищает оба порядка и при прямой записи через
триггеры. Область определяется потоком, утверждённым планом с позицией
учебного плана, событием и постоянным курсом получателя. Исправление ранее
опубликованной попытки по-прежнему подчиняется правилам БРС. При будущем
переносе результатов учебной работы потребуется отдельная команда с проверкой
этой области и явным контролем появления второго источника.

Исправление проверки создаёт очередную версию с автором, временем и основанием
длиной 3–500 символов. Предыдущее состояние хранится в предыдущей версии той же
попытки. SQLite проверяет новые комментарии, время и основание, защищает от
изменения, удаления и замены зарегистрированных сдач. Для технического исправления применяется та же добавочная запись
с проверкой полномочий и указанием основания. Если обычная команда недоступна,
потребуется отдельная согласованная процедура с аудитом. Для уже существующих
версий миграция не дописывает вымышленные основания. Ранее сохранённые
совпадения coursework и БРС остаются для ручной сверки.

Миграция 0019 запрещает удаление и замену опубликованных заданий и заданий
со связанными получателями, попытками или проверками. Получателя с историей
нельзя удалить. Эти проверки действуют и при `foreign_keys=OFF`.
Существующие триггеры по-прежнему защищают родительские ключи при UPDATE
и ключ записи получателя при REPLACE. Черновик без связей можно удалить.
При обнаружении прежних осиротевших записей мигратор требует сверки данных
и останавливается на проверке внешних ключей.

Перенос баллов и PDF остаются следующей итерацией. Для PDF отдельная таблица
ссылается на конкретную попытку через ключ задания, курса и номера попытки.
Публикация результата в БРС должна требовать отдельной команды. После закрытия
периода пересмотр одобряет деканат, а исправление выполняет назначенный
преподаватель. Официальная аттестация остаётся в действующем контуре.

## Резервное копирование SQLite

На Linux CLI использует `/opt/mgimov/backups/daily`. Оператор создаёт этот
закрытый каталог с правами 0700 и владельцем, совпадающим с пользователем
задания. Команда отклоняет симлинки в пути и родителей с записью для группы
или остальных. До включения cron оператор проверяет действующие root/alias
Nginx и отсутствие HTTP-доступа к каталогу. Запускать от непривилегированного
пользователя с доступом к SQLite и правом записи в ежедневный каталог.
На Windows ежедневный каталог должен иметь защищённую DACL, а его предки
должны пройти проверку цепочки как для приватной копии P0.1. Ручные снимки
хранить отдельно. Выделяйте один ежедневный каталог одному логическому
источнику: формат комплекта хранит дату и SHA-256, идентификатора источника нет.

SQLite и SHA-256 публикуются одним переименованием каталога
`daily-ГГГГ-ММ-ДД/` после проверки целостности, внешних ключей и истории миграций.
Следующий запуск проверяет staging, завершает публикацию пригодного снимка
или перемещает остатки в закрытый карантин и пишет предупреждение.
При семи карантинных записях дальнейший карантин требует действий оператора.
`--keep-successful` сохраняет не менее семи последних подтверждённых
ежедневных комплектов по UTC. Пропуск дней не уменьшает это число. Ротация
выполняется после публикации либо проверки комплекта текущей даты.
Повтор в тот же день возвращает уже проверенный снимок. При ошибке проверки
команда сообщает об отказе и сохраняет комплект для оператора. Плоские пары
старого формата, ручные копии, повреждённые и несовместимые со схемой
комплекты исключены из ротации. Квота включает все обычные файлы
в каталоге, в том числе ручные копии, остатки и временные снимки.
До копирования проверяется свободное место с запасом под WAL и новый снимок.
Оставьте запас под восьмой файл. При исчерпании квоты или нехватке места
предыдущие копии сохраняются. Проверьте остатки и карантин или увеличьте
квоту после проверки свободного места.

Перед настройкой подтвердите путь к фактически открытой SQLite работающей
службы. Например, для проверки открытых дескрипторов из Shell ispmanager:

```bash
pid=$(systemctl show -p MainPID --value mgimov.service) && test "$pid" -gt 0 && ls -l "/proc/$pid/fd" | grep -E '\.sqlite3($|-wal|-shm)'
```

Подключения могут быть краткоживущими. Если дескриптор не виден, отдельно
сверьте точное значение `MGIMOV_DB_PATH` из конфигурации действующей службы
или её окружения, выводя только эту переменную. Если она отсутствует,
подтвердите эффективный путь до настройки задания. Заполните
`MGIMOV_DB_PATH` в crontab и отдельно подставьте подтверждённый абсолютный путь
в `--db`. На Linux CLI требует совпадения путей, отвергает SQLite из
проектного `.tmp` и использует только выделенный закрытый каталог.
Перед расписанием выполните ту же команду вручную от пользователя задания.
Время расписания соответствует часовому поясу cron на VPS, а дата комплекта
определяется по UTC. Убедитесь, что оба запуска относятся к одной UTC-дате и
что второе задание запускается после штатного предела времени первого.

Команда проверки свежести читает только опубликованный комплект ровно за
ожидаемую UTC-дату. По умолчанию проверяется текущая дата UTC. `--date
YYYY-MM-DD` позволяет явно проверить выбранный день. Проверяются SHA-256,
целостность SQLite, внешние ключи, схема и контрольные суммы миграций
текущего релиза. Staging, карантин и старые комплекты не заменяют ожидаемую
копию. Exit 0 означает, что комплект проверен. Exit 1 означает ошибку или
отсутствие комплекта. Exit 2 означает ошибку аргументов. Вывод содержит
только UTC-дату и общую категорию результата.

```powershell
& .\.venv\Scripts\python.exe -B -m backend.commands.check_backup --directory "$backupDir" --date 2026-11-16
```

Пример для будущего использования. `local-admin` заменяется существующим
локальным получателем после проверки доставки. Каждое задание помещается
в одну строку crontab. Журнал получает вывод команды, а cron получает только
фиксированный текст при ошибке. `pipefail` сохраняет отказ команды при
успешном выполнении `logger`.

```cron
MGIMOV_DB_PATH=/absolute/confirmed/service-database.sqlite3
MAILTO=local-admin
0 3 * * * /bin/bash -o pipefail -c '(cd /opt/mgimov/app && timeout --kill-after=15s 10m .venv/bin/python -B -m backend.commands.backup_database --production --db "/absolute/confirmed/service-database.sqlite3" --directory /opt/mgimov/backups/daily --keep-successful 7 --max-bytes 1073741824) 2>&1 | logger -t mgimov-backup >/dev/null 2>&1 || { printf "MGIMOv backup job failed\n"; exit 1; }'
30 3 * * * /bin/bash -o pipefail -c '(cd /opt/mgimov/app && timeout --kill-after=15s 5m .venv/bin/python -B -m backend.commands.check_backup --directory /opt/mgimov/backups/daily) 2>&1 | logger -t mgimov-backup-check >/dev/null 2>&1 || { printf "MGIMOv daily backup freshness check failed\n"; exit 1; }'
```

Проверка свежести должна выполняться отдельным заданием, чтобы обнаруживать
также пропущенный запуск backup. Linux cron и доставка локального письма —
NOT VERIFIED. Если почта недоступна, теги `mgimov-backup` и
`mgimov-backup-check` пригодны для существующего локального мониторинга;
запись в журнале сама по себе не доставляет сообщение администратору.
Файл блокировки остаётся на месте, блокировка снимается
ядром при завершении процесса. Старый каталог блокировки предыдущей версии
можно убрать после проверки, что предыдущий процесс остановлен. Старые
плоские пары и карантин проверяет оператор. Остатки учитываются в квоте.
Параметр `--keep-days` принимается с предупреждением и означает число
успешных комплектов. Проверка действующего расписания на VPS требуется
до изменения параметров ротации.

Для репетиции используйте отдельную приватную копию нужного релиза и синтетический
опубликованный комплект. Укажите абсолютный путь к ежедневному каталогу, UTC-дату
и новый файл внутри `.tmp` тестового проекта. Родитель создаётся заранее с
защищённой DACL на Windows или режимом `0700` на Linux. Файловая система должна
поддерживать жёсткие ссылки для атомарной публикации без перезаписи.

```powershell
& .\.venv\Scripts\python.exe -B -m backend.commands.restore_database --backup-directory "$backupDir" --date 2026-11-16 --output "$restoreFile" --confirm-test-restore
```

```bash
.venv/bin/python -B -m backend.commands.restore_database --backup-directory "$backup_dir" --date 2026-11-16 --output "$restore_file" --confirm-test-restore
```

Команда проверяет SHA-256, целостность, внешние ключи и миграции выбранного
релиза. Staging, карантин, неподтверждённые файлы и существующее назначение
отклоняются. Запустите `backend.commands.diagnose --db <путь-к-копии>` и
проверьте health и вход на отдельном экземпляре с этой копией. Для аварийного отката подтвердите пару
кода и схемы, остановите службу, сохраните текущую БД новым согласованным снимком,
проверьте отсутствие активных WAL/SHM, затем атомарно установите проверенную копию
в каталоге приложения. Проверьте владельца, права, диагностику и health после
запуска. Если после снимка были новые записи, оцените их перенос до замены.
До публикации PDF нужен единый комплект SQLite и файлов. Вложения неизменяемы
и фиксируются в закрытом хранилище до коммита ссылки в SQLite. Очистка удаляет
только незавершённые или неиспользуемые файлы после сверки ссылок. Снимок и
очистка используют общую блокировку, чтобы нужный снимку объект не исчез.
Из снимка строится манифест файлов с размером и SHA-256. Комплект публикуется
только после проверки полноты. Ротация и восстановление работают с комплектом
целиком. До production проверить параллельные загрузки, очистку и отказ при
отсутствующем или повреждённом вложении.

### P0.2b — репетиция восстановления и отката

Используйте отдельный приватный checkout, синтетическую SQLite и loopback.
На Windows повторите создание приватной копии из P0.1. При копировании
добавьте `tests` и `requirements-test.txt` к перечисленным путям. Из этой
копии с доступным окружением тестов запустите:

```powershell
& .\.venv\Scripts\python.exe -B -m unittest tests.test_recovery_rehearsal -v
```

Тест запускает собственные процессы Uvicorn на свободных loopback-портах.
Синтетические пароли создаются в памяти. Кандидат обновления получает
собственные файлы приложения и БД. Временные файлы теста удаляются после
завершения. Windows требует защищённую DACL и поддержку жёстких ссылок.

#### Ручная последовательность для изолированной Ubuntu 24.04

1. Подготовьте отдельный стенд с тестовым приложением, непривилегированной
   учётной записью, приватными каталогами и синтетической БД. Для Linux CLI
   используйте подтверждённый абсолютный путь внутри тестового проекта вне
   `.tmp` и `/opt/mgimov/backups/daily` **только внутри стенда**. Зафиксируйте
   SHA-256 исходной SQLite после остановки первоначального тестового процесса,
   версию кода, миграции, роли и контрольные данные API. Если есть WAL,
   перед переносом создайте согласованный снимок через штатный Backup API.
2. Создайте комплект действующим CLI `backup_database` с `--production`,
   идентичными значениями `MGIMOV_DB_PATH` и `--db`, а также параметрами из
   раздела выше. Сверьте SHA-256 в комплекте. Выполните `restore_database`
   с UTC-датой этого комплекта в новый файл приватной `.tmp` той копии проекта,
   чей код соответствует схеме. До старта приложения сравните SHA-256 копии
   с комплектом и выполните `backend.commands.diagnose --db "$restore_file"`.
3. Запустите восстановленную копию на отдельном loopback-порту. Проверьте
   `200` от `/api/health`, авторизацию Student/Staff, расписание, БРС, зачётку,
   очередь Coursework, попытки и проверки. Сравните с контрольными значениями.

   ```bash
   MGIMOV_DB_PATH="$restore_file" MGIMOV_ORIGIN=http://127.0.0.1:18031 .venv/bin/python -B -m uvicorn backend.app:app --host 127.0.0.1 --port 18031 --no-proxy-headers
   ```

4. В ещё одной тестовой копии добавьте ожидаемую миграцию `0020` для
   репетиции и оставьте её неприменённой на отдельной тестовой БД. Готовность
   кандидата должна вернуть `503`. Остановите только его PID. Дождитесь выхода
   процесса и завершения всех других тестовых писателей. Попытка SQLite
   `BEGIN EXCLUSIVE` с нулевым тайм-аутом должна завершиться успехом с
   последующим `ROLLBACK`. Для WAL отдельно выполните
   `PRAGMA wal_checkpoint(TRUNCATE)` и проверьте, что `busy=0`. Если БД занята,
   остановитесь. Сохраните БД кандидата и её sidecar-файлы до разбора.
5. Для rollback снова выполните CLI restore в новый файл **предыдущей версии**
   приложения. При остаточных `-wal`, `-shm` или `-journal` у выбранного имени
   выберите новое имя. Запустите предыдущую версию с явным `MGIMOV_DB_PATH`
   на эту базу и повторите проверки шага 3. Повторный rollback выполняйте в
   ещё один новый файл. Сверьте неизменность исходной SQLite и комплекта.

Точка отката задана опубликованным снимком. Более новые записи могут
отсутствовать после отката, поэтому отдельно сохраняйте состояние кандидата
и фиксируйте, какие изменения нужно разобрать до переключения. Тестовая
репетиция переключает пару «каталог кода + `MGIMOV_DB_PATH`» и работает с
собственными процессами Uvicorn. Механизм переключения службы Linux,
реальный `ENOSPC` и доставка уведомлений требуют отдельной проверки.
Снимок включает таблицу серверных сессий. Перед боевым восстановлением
нужна согласованная политика отзыва сессий, восстановленных из снимка.

## Конкурсная демосреда P0.1

На Windows подготовьте отдельную копию приложения под профилем текущего
пользователя. SQLite останется внутри этой копии. Рабочий checkout в
`C:\Projects\MGIMOv` не подходит, если любой компонент пути, включая `.tmp`,
даёт посторонним права изменения или удаления. Права существующих папок
команда сохраняет.

Из корня проверенного исходного checkout в закрытом интерактивном PowerShell:

```powershell
$private = & python -B -c "from pathlib import Path; from backend.commands.contest_demo_permissions import PrivateDemoDirectory; print(PrivateDemoDirectory(Path.home()).path)"
if ($LASTEXITCODE -ne 0 -or -not $private) { throw 'Приватный каталог недоступен' }
$files = @(git ls-files --cached --others --exclude-standard -- backend frontend requirements.txt constraints.txt | Sort-Object -Unique)
if ($LASTEXITCODE -ne 0 -or -not $files) { throw 'Не удалось получить список исходников' }
foreach ($file in $files) {
    $target = Join-Path $private $file
    [IO.Directory]::CreateDirectory((Split-Path -Parent $target)) | Out-Null
    Copy-Item -LiteralPath $file -Destination $target -ErrorAction Stop
}
Set-Location -LiteralPath $private
python -m venv .venv
python -m pip --python .venv install -r requirements.txt
```

Затем из этой копии запустите seed. На POSIX используйте приватный checkout
с настроенной `.venv`.

```powershell
.\.venv\Scripts\python.exe -B -m backend.commands.seed_contest_demo --confirm-demo
```

Введите три новых разных синтетических пароля для `s01`, `s02` и `t01`.
Пароли вводятся скрыто, хранятся только как Argon2id и не выводятся. Команда
пишет путь `DEMO_DB` новой SQLite внутри `.tmp/contest-demo-*/`. Повторный
запуск создаёт отдельную чистую среду, сохраняя прежние базы. Базовый seed
RC3.1 создаёт ещё 17 синтетических аккаунтов со случайными паролями, которые
не выдаются. Для показа используются только три указанных аккаунта.

На Windows каталог создаётся сразу с защищённой DACL. Разрешение FullControl
с наследованием на дочерние файлы и каталоги получают только SID текущего
пользователя, SYSTEM (`S-1-5-18`) и BUILTIN Administrators (`S-1-5-32-544`).
Проверка читает фактические правила до создания SQLite, после создания
проверяет саму базу и присутствующие `-journal`, `-wal`, `-shm`. Любое
постороннее правило на каталоге запуска или базе вызывает отказ. Отдельно
проверяются владелец, действующие ACE и отсутствие reparse points в каждом
каталоге от корня локального диска до родителя запуска. Чтение и проход по
предкам допустимы. Чужие права на изменение, `DELETE`, `DELETE_CHILD` или
смену ACL недопустимы. Корень диска может разрешать создание соседних папок,
если чужие пользователи не могут заменить существующие компоненты пути.
На другом компьютере проверка может отклонить и каталог профиля.

Если создание или проверка прав не проходят, подготовка завершается
с ошибкой. До успешной проверки каталога база не создаётся. Если папка уже
создана, сообщение указывает точный путь отдельного запуска для осмотра и
ручной очистки. Остановите сервер и удалите только созданную папку запуска
или всю отдельную копию приложения, если она больше не нужна. На Windows
нужен локальный фиксированный диск с DACL и Windows PowerShell для чтения
прав. Junctions, символьные ссылки и другие reparse points отклоняются.
Проверка рассчитана на других непривилегированных пользователей. Текущая
учётная запись, системные администраторы и системные процессы доверены.
На POSIX применяется проверка владельца и режима 0700 каталога, для файлов
базы и присутствующих sidecar — режим 0600. Этот путь на Linux/macOS в данном
прогоне не проверялся.

```powershell
$demoDb = Read-Host 'Скопируйте значение DEMO_DB'
if (-not (Test-Path -LiteralPath $demoDb -PathType Leaf)) { throw 'Демобаза не найдена' }
$env:MGIMOV_DB_PATH = $demoDb
$env:MGIMOV_ORIGIN = 'http://127.0.0.1:8030'
.\.venv\Scripts\python.exe -B -m uvicorn backend.app:app --host 127.0.0.1 --port 8030 --no-proxy-headers
```

Откройте `http://127.0.0.1:8030/`. Ctrl+C останавливает сервер. Если порт
занят, замените его одновременно в origin, команде и адресе браузера.
Используйте отдельные профили браузера либо завершайте сессию перед сменой
пользователя. При необходимости проверьте копию командой
`.\.venv\Scripts\python.exe -B -m backend.commands.diagnose --db $demoDb`.

1. Войдите как `s01` (ДЕМО-А). В «Расписании» откройте занятие на сегодня.
   В «Аттестациях» покажите опубликованные баллы БРС, в «Зачётке» — официальный результат.
2. В «Учебных работах» откройте «Демо A · Разбор учебного кейса» и отправьте текст.
3. Войдите как `t01`. Откройте ту же работу и сдачу участника S01.
   Выберите «На доработку», добавьте комментарий и сохраните решение.
4. Вернитесь к `s01`, обновите работу и отправьте новый текст. Под `t01`
   проверьте вторую сдачу, выставьте 8 из 10 и покажите сохранённую историю.
   Баллы этой работы хранятся отдельно от опубликованных баллов БРС и зачётки.
5. Войдите как `s02` (ДЕМО-Б). В списке есть только «Демо B · Сравнение
   учебных аргументов» и собственные расписание, БРС и зачётка.

Срок работы задан относительно подготовки. После срока сдача отмечается
просроченной. Назначения преподавателя действуют семь дней. Для свежего показа
или повтора сценария с нуля подготовьте новую копию и используйте её `DEMO_DB`.

## Локальный Git checkpoint

Предложение для отдельного разрешения на коммиты. Начать из корня проекта
на `main` с HEAD `d1c24df84baea88d8e7a50608ff4b676d71d939a` и пустым индексом.
Сверить `git status --short` с перечнем ниже. При расхождении остановиться.

```powershell
git branch --show-current
git rev-parse HEAD
git status --short
git diff --cached --name-only
git add -- backend/commands/backup_database.py backend/migrations/manager.py tests/test_backup_database.py tests/test_foundation.py
git diff --cached --name-only
git diff --cached --check
git diff --cached
# После проверки ровно четырёх путей и содержимого индекса:
git commit -m "feat: add verified SQLite backups"
git show --stat --oneline HEAD
```
