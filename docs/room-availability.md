## Модель и граница достоверности

Миграция `0025_room_availability.sql` добавляет только `building_open_hours`
и `room_unavailability`; прежние миграции и таблицы расписания не изменены.
Недельный ключ `(building_id, weekday)` уникален, weekday — 0 (понедельник)…6.
Одна запись задаёт один рабочий интервал в минутах [0,1440]; оба NULL означают
явно закрытый день. Отсутствие записи означает неизвестный режим, а не закрытие.
Частично NULL, нулевая длительность и дубли недельного правила запрещены SQL.
Несколько рабочих окон за день не поддерживаются первой версией.

Ограничение помещения действует на полуоткрытом интервале Unix seconds
`[starts_at, ends_at)`; NULL конца означает постоянную недоступность начиная
с указанного момента. Причина служебная и через поиск не возвращается.
Внешние ключи RESTRICT сохраняют связи; индекс room/start/end ускоряет поиск.
Перекрывающиеся ограничения допустимы: любое из них исключает помещение.

Данные читаются в одной SQLite-транзакции: все scheduled lessons независимо
от группы и действующие attestation_slots. Отменённые занятия исключены;
переносы читаются из актуальных date/room/start/end lessons, не из уведомлений.
Для аттестаций используется существующая семантика terminal events
cancelled/excused/unexcused/published/completed. Предыдущее назначение после
отмены не занимает помещение; новое назначение учитывается непосредственно.
Пересечение: start < requested_end AND end > requested_start. Смежность допустима.
Часовая зона интервала — Europe/Moscow, календарный день 1900–2100.

Свободно **по учтённому расписанию**, без бронирования и гарантии доступа.
Внешние мероприятия и не внесённые в MGIMOv занятия неизвестны.
Результат может устареть после изменения расписания: нужно повторить поиск.
Подтверждение полноты расписания не требуется согласно решению пользователя.

## HTTP

Серверная сессия Student/Staff обязательна. UI доступен Student.

- `GET /api/v1/me/rooms/catalogue` → `{buildings:[{id,name}]}`.
- `GET /api/v1/me/rooms/availability?date=2027-03-01&start=10:00&end=10:30&building=building&capacity=20`.

date/start/end обязательны; building необязателен; capacity по умолчанию 1,
целое 1…1000. Только конец допускает 24:00. Повторные/неизвестные параметры,
неизвестный корпус и некорректный интервал → 422; без сессии → 401.
503 — недоступная БД/неприменённая миграция. Запросы не пишут в SQLite.

Ответ: `{items:[{id,number,capacity,building_id,building,access_rules}],
date,start,end,timezone:'Europe/Moscow'}`. access_rules = known | unknown.
known означает наличие разрешающего недельного правила для всего интервала.
Закрытые и занятые помещения отсутствуют в ответе. unknown показывается отдельно:
«Режим доступа не подтверждён». Нет ФИО, групп, дисциплин, оценок, причин
ограничений и сведений о том, кто занимает помещение.

## Интерфейс и сессии

Student → «Поиск аудиторий» / `/#rooms`. Поля даты, времени, корпуса и
вместимости; RU/EN, загрузка, ошибка и пустой результат. Названия из SQLite
выводятся через textContent. Данные не сохраняются в localStorage.
Смена владельца/роли очищает результаты и форму; старые HTTP-ответы игнорируются.
Текущий защищённый 401 вызывает существующую центральную очистку сессии.
Тайм-аут запроса — 10 секунд. При ошибке старый результат скрывается.

## Демоданные и эксплуатация

Не установлены реальные часы работы университета. Браузерная фикстура использует
явно синтетические часы и три помещения; автоматического изменения рабочей базы нет.
Для финальной демобазы нужно отдельно согласовать воспроизводимое наполнение
корпусов/аудиторий (например 50), расписания всех групп, аттестаций, тестовых часов
и ограничений. Отсутствующие часы остаются unknown. API редактирования этих правил
и бронирование в данную задачу не входят. Подготовка только на изолированной базе.

Миграции применяются явно существующим CLI; перед обновлением — проверенный
backup согласованной пары кода/данных. Backup/restore должны использовать релиз
с той же цепочкой до 0025. Linux/VPS в этой задаче не проверялись и не менялись.

## Исправления после REJECT Luna

Тест миграции разделён на независимые успешный и ошибочный сценарии. Оба
сначала создают собственную заполненную базу строго 0001–0024, явно проверяют
24 applied/0025 pending, затем используют отдельный полный каталог 0001–0025.
Успешный сценарий проверяет создание backup, полный логический dump старой базы
в backup, сохранность зданий/помещений, новые таблицы и единственную запись 0025,
повтор без изменений и без ненужного backup. Ошибочный сценарий добавляет
несуществующий SELECT в отдельную копию SQL, сравнивает весь dump до/после,
проверяет отсутствие обеих таблиц, индекса и записи 0025, затем успешный retry.
Production SQL 0025 не менялся.

Результаты поиска объявляются через единственный существующий #rooms-status
(role=status, aria-live=polite): общее количество и количество с неизвестным
режимом, пустой результат либо ошибка. Карточки не помещены во вторую live-region.
Проверки DOM в Chrome подтверждают текст и атрибуты; фактическая речь NVDA/JAWS
в этой задаче не проверена.
