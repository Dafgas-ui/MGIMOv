# Передача независимых проверок

Обновлено: 4 ноября 2026 года, МСК.

## Правило записи

Astra по умолчанию читает проект и возвращает отчёт в своём чате; замечания
не записывает непосредственно в рабочий код и не исправляет их сама.
Sol после согласования с пользователем переносит результаты в этот файл,
сохраняя различие между подтверждёнными проблемами и потенциальными рисками.
Приоритеты и архитектурные решения утверждает пользователь. Секреты и полные
диалоги сюда не копируются. Оба чата не редактируют одни файлы параллельно.

## Потенциальные риски

R-01 — низкая серьёзность на V2: общедоступный health вызывает status(), затем
полную проверку SQLite (integrity_check/foreign_key_check, схему и историю).
Доказательства: [маршрут](../../backend/app.py), health(),
[менеджер](../../backend/migrations/manager.py), status()/inspect().
При частых запросах и росте базы возможна нагрузка. Внешняя достижимость,
конфигурация прокси и эффект нагрузки не проверялись; DoS не доказан.

W-02 — предупреждение приёмки о совместимости Starlette/httpx. Ранее
зафиксировано предупреждение об устаревающей поддержке httpx в TestClient:
[результаты V2](../test-results.md). Независимая приёмка сохранила предупреждение,
хотя тесты прошли. Подтверждённой функциональной блокирующей ошибки здесь нет.

## Рекомендации

Рассмотреть лёгкую readiness-проверку, а полную integrity-проверку выполнять
отдельно. Перед изменением согласовать задачу. Динамический сценарий — только
с отдельным разрешением, на изолированной среде, с ограниченной нагрузкой.
В будущей V3 проверить вход/выход, отзыв сессий, cookies/CSRF, чужие ID,
анонимный доступ и границы сотрудника. Оценить совместимость тестового клиента отдельно. Аудит зависимостей и
оставшиеся браузерные сценарии остаются неподтверждёнными.

### Узкая повторная приёмка RC4.2

## RC4 — P0.1 конкурсная демосреда

Рабочее дерево поверх `494007a`. Команда использует сценарии seed RC3.1
и добавляет две работы разных групп через существующий сервис. Luna может

Сквозной тест подтверждает возврат, повторную сдачу, сохранение истории

[Команды и сценарий](../rc4-foundation.md#конкурсная-демосреда-p01).

### Повторная проверка ACL для P0.1

Windows ранее наследовала доступ Users и Authenticated Users из `.tmp`.
Новый каталог сразу создаётся с защищённой DACL и проверяется до SQLite.
Luna может повторить тесты `tests.test_contest_demo` под Windows и проверить
фактические SID каталога, базы и sidecar. Тест с намеренно небезопасным
наследованием должен вернуть путь пустой папки и отказ без создания SQLite.

### Повторная проверка цепочки путей Windows для P0.1

Для позитивного сценария используйте приватную копию из инструкции P0.1.
На исходном checkout с правом Modify у Authenticated Users ожидается отказ.
В приватной копии `tests.test_contest_demo` проверяет реальные DACL каталога,
SQLite и sidecar. Отдельные тесты проверяют отказ при junction и при выдаче
`DELETE_CHILD` постороннему SID после первичной проверки checkout. При отказе
в этих тестах SQLite отсутствует. После финальной проверки защита зависит
от прав всей цепочки. Конкурентная операция из отдельной учётной записи
Windows после финальной проверки отдельно не воспроизводилась.

После третьего аудита изменены только тестовые фикстуры. Тест `DELETE_CHILD`
читает DACL после установки права `0x40` для `S-1-5-11` и восстанавливает
исходную DACL своей папки при завершении. Тест junction проверяет атрибут
reparse point, тип mount point и фактическую цель. Если среда не позволяет
создать нужное условие, соответствующая проверка отмечается SKIP.
[Результаты повторного прогона](../test-results.md#p01--повторная-проверка-двух-windows-фикстур).
