### Запуск для Astra

Подробная автономная инструкция: [RELEASE.md](../../RELEASE.md) и её точная копия
в ZIP. В распакованном RC создать `.venv`, установить requirements-test.txt,
создать **новую** БД командой `seed_mvp_demo --db .tmp/rc-demo.sqlite3 --confirm-demo`.
Этот seed явно применяет 0001–0006, отказывает для существующей/рабочей базы и
предлагает скрытый ввод пяти паролей. Не переносить старые SQLite/DPAPI.

Для сервера задать одинаковый port/origin:

```powershell
$env:MGIMOV_DB_PATH = '.tmp/rc-demo.sqlite3'
$env:MGIMOV_ORIGIN = 'http://127.0.0.1:8030'
.\.venv\Scripts\python.exe -B -m uvicorn backend.app:app --host 127.0.0.1 --port 8030 --no-proxy-headers
```

Адрес `http://127.0.0.1:8030`, остановка Ctrl+C. Если порт занят — выбрать другой
и изменить оба значения; чужие серверы не останавливать. Проверки этой задачи
использовали свободные случайные loopback-порты. Браузерный сервер RC на 51454
остановлен по проверенным PID/команде. Другие процессы и порты 8000/8027 не трогались.

## B. Исправления

| Дефект | Причина | Решение | Доказательство |
|---|---|---|---|
| MVP-01 | Разные тексты 404 для отсутствующего студента/занятия и отказа group_scope | `group_scope`, `edit_lesson`, `mutate` возвращают одинаковые 404/JSON; scope проверяется до проверки версии/ссылок и записи | `test_mvp01_identical_denials_no_side_effects`, реальный HTTP `denied_pairs`: тело/статус равны, notifications/lessons/lesson_changes/audit неизменны |
| MVP-02 | Кнопка подписи строилась только по первым 20 записям нового обзора | Выпуск/передача доступны в деталях выбранного обращения существующей пагинированной очереди. Staff-detail дополнен metadata `document`; контроллер использует прежние sign/deliver API | Очередь 36 записей, старая заявка на второй странице, подпись и передача владельцу; чужой 404, scope 404, старая version 409 |
| MVP-03 | Жёсткий LIMIT 100 без продолжения, unread count учитывал недоступные старые записи | Keyset cursor по `(created_at DESC,id DESC)`, LIMIT 101 для определения продолжения, добавочный `next_cursor`; frontend next/previous, сохранение страницы при чтении/refresh | 110 новых уведомлений плюс исходные, все ID без пропусков/повторов, одинаковые timestamps, новые события между страницами, unread -1, B не читает и не меняет A |

MVP-01: [deanery/service.py](../../backend/deanery/service.py), `group_scope`,
`edit_lesson`, ветка `notify` в `mutate`. Отказы остаются внутри транзакции с rollback,
не создают ложного успешного аудита. Разрешённые операции повторно прошли в полном
MVP-сценарии. Это исправление наблюдаемого различия ответов, не утверждение о
полном отсутствии любых побочных каналов.

MVP-02: [requests/service.py](../../backend/requests/service.py), `details` выдаёт
`document` только после объектной Staff-проверки. [requests-state.js](../../frontend/js/requests-state.js),
`certificate`, сохраняет ID выбранной **заявки**, передаёт её version и ожидаемый
аккаунт/CSRF. После sign/deliver заново читает детали; не повторяет POST автоматически.
[requests.js](../../frontend/js/requests.js), `renderRequests`: кнопки в деталях,
подпись только одобренной справки, передача подписанной, метка передачи и демоподписи.
Прежние серверные правила не дублируются и остаются источником истины.
[mvp.js](../../frontend/js/mvp.js) больше не создаёт отдельную кнопку подписи из
первой страницы; содержит переход к существующей очереди и прежний ответ сотрудника.

MVP-03: [deanery/routes.py](../../backend/deanery/routes.py), `notices` принимает
единственный `cursor`; прочие/повторные параметры отклоняет. `read` и
`notification_boundary/notification_cursor` ограничивают формат и сохраняют SQL
фильтр владельца независимо от содержимого cursor. `items/unread` совместимы с
прежним первым запросом без параметров; `offset` не вводится — используется cursor.
Счётчик и страница читаются в одной read-транзакции. Прочтение не влияет на сортировку.
[mvp-state.js](../../frontend/js/mvp-state.js) сохраняет позицию для того же аккаунта,
сбрасывает её при смене личности/выходе; поздние ответы и скрытие защищены прежним
поколением запросов. Новый API не превращает cursor в средство авторизации.

Не менялись SQL-миграции, авторизация, серверные роли/CSRF, index.html, account.js,
CSS и настройки Luna. Изменены функциональные модули Sol; G/R1/R2/R3 не внедрялись.

### Реальный браузер на чистом RC

ChatGPT in-app Chromium; отдельная новая SQLite внутри копии RC, 36 обращений,
129 непрочитанных уведомлений A (110 добавленных плюс исходные события).

Выполнено при 360×800:

1. Student A вошёл, открыл «Старые уведомления», увидел последнюю карточку по
   стабильному порядку. Прочитал её: общий unread **129 → 128**, старая страница
   сохранилась, появился «Прочитано». Переход назад к новым уведомлениям работает.
2. Staff вошёл, нажал «Следующие обращения», открыл старую одобренную справку,
   подписал и передал её непосредственно из деталей. Интерфейс показал подтверждение.
3. Student A после нового входа открыл новую справку с назначением `RC old page`;
   у него две справки. Student B после отдельного входа имеет только свою одну;
   прямой чужой доступ дополнительно отклонён в HTTP-тестах.

В проверенном мобильном состоянии горизонтального переполнения нет: viewport 360,
document scrollWidth 345. Снимки [уведомления](../../.tmp/rc-old-notifications.jpg)
и [передача старой справки](../../.tmp/rc-old-certificate.jpg). Тестовые сессии завершены,
viewport override сброшен, вкладка закрыта, собственный сервер остановлен.
Временные credentials этой НОВОЙ фикстуры защищены отдельным DPAPI внутри проверенной
копии и отсутствуют в ZIP/pristine-копии; старые DPAPI не использовались.

Не проверялись исчерпывающая доступность, все браузеры/размеры/реальные телефоны,
нагрузка/DoS, полная визуальная регрессия. Новый реальный сценарий не называется
независимой приёмкой Astra.

## D. Остаточные риски и ограничения

- Starlette/httpx выдаёт прежнее deprecation warning; оба новых окружения и тесты
  работоспособны, замена зависимостей вне текущей задачи. Полный supply-chain аудит
  не проводился; в релиз входят проверенные закреплённые версии и их hashes.
- RC установлен и проверен на Windows/Python 3.13.1. Другие ОС и версии Python
  не объявляются проверенными. Wheelhouse содержит Windows wheels; для другой
  платформы использовать её совместимые packages из тех же закреплённых требований.
- Ограничение нового обзора 200 занятиями/студентами остаётся; массовая навигация
  расписания не входит в три исправления. Справки из глубокой очереди теперь доступны
  через выбранные детали, прежнее ограничение MVP-02 снято.
- Cursor обеспечивает последовательность существующих уведомлений без сдвига
  offset при чтении/новых событиях; поступившие новые события видны на первой
  странице после возврата/обновления. Нет push и юридически значимой ЭП.
- HTTPS/proxy/VPS/публичный периметр не проверялись и не менялись. Публичная готовность
  и официальное конкурсное соответствие не объявляются.
