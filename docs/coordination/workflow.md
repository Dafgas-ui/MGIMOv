# Взаимодействие Sol, Astra, Luna и пользователя

Обновлено: 5 ноября 2026 года, МСК.
Sol и Luna — разработчики согласованных этапов; перед каждой задачей их файлы
и ответственность явно разграничиваются. Luna отвечает прежде всего за интеграцию
интерфейса и пользовательские настройки. Astra — независимый архитектор и аудитор;
по умолчанию только чтение. Имена обозначают роли чатов, не автоматические процессы.
Все работают с одним репозиторием и одной рабочей директорией.

## Общий контекст

Перед началом каждой задачи каждый агент читает актуальные [статус](project-status.md),
[задачи](task-board.md), [передачу проверок](review-handoff.md), затем релевантные
[архитектуру](../architecture.md), [решения](../decisions.md),
[перенос компонентов](../component-migration.md), [результаты тестов](../test-results.md)
и [журнал ИИ-разработки](../ai-development-log.md). Проверить текущие Git
HEAD/status/diff и активные задачи командами без изменения состояния.
Документы — общий источник состояния, но при расхождении с кодом/Git нужно
сообщить пользователю, а не автоматически переписать историю или игнорировать diff.

Разные чаты не знают переписку друг друга автоматически. Пользователь передаёт
задачу и указывает эти документы. Нет фоновой синхронизации, сервиса или агентов.
Полные чаты в документы не копируются; записываются краткие решения и доказательства.

## Рабочий цикл

1. Пользователь утверждает задачу, границы и разрешённые действия; пользователь
   принимает окончательные решения по приоритетам и изменениям архитектуры.
2. Для каждого этапа в task-board указывается конкретный исполнитель и область файлов.
3. Назначенный исполнитель читает актуальные документы, проверяет активные задачи
   и Git status/HEAD/diff.
4. Sol и Luna выполняют только порученную им область, сохраняя существующие изменения.
   Если задачи затрагивают одни файлы, они выполняются последовательно: параллельное
   редактирование Sol и Luna одного файла запрещено.
5. Исполнитель выполняет необходимые разрешённые проверки; записывает команду, ревизию,
   результат и ограничения. Пропущенная проверка не считается успешной.
6. Исполнитель обновляет статус и задачи, фиксирует результаты и передаёт завершённый
   этап Astra на независимую проверку с точной ревизией или diff.
7. Astra читает актуальные документы и исходный код, не полагаясь только на отчёт
   исполнителя, и фиксирует замечания в существующем [review-handoff](review-handoff.md).
8. Astra возвращает отчёт с доказательствами, отделяя находки от рисков.
9. Пользователь принимает решение: исправление, уточнение, отдельная проверка,
   изменение приоритета или отсрочка.
10. Назначенный разработчик переносит согласованный результат в handoff, исправляет
    только разрешённое, проверяет и обновляет документы. Повторная проверка Astra —
    по отдельному запросу.

## Защита от конфликтов

Sol и Luna не изменяют одни и те же файлы параллельно; task-board и явное сообщение
о границах задачи определяют владельца затронутых файлов. Если область пересекается,
один исполнитель ждёт завершения и передачи файлов другим. Sol и Astra не изменяют
одни и те же файлы параллельно. У общего каталога нет
автоматической изоляции. На время обзора Sol сохраняет проверяемое состояние
неизменным либо сообщает новый HEAD/diff; аудит явно отмечает смену состояния.
Astra не пишет ни в код, ни в документы без отдельного разрешения. Исключение
на запись согласуется по конкретным файлам и времени; оно не разрешает исправлять код.

При неожиданных чужих изменениях не делать reset/checkout/clean, не затирать файлы;
установить их происхождение и согласовать продолжение с пользователем.
Не создавать коммиты, не публиковать и не менять scope по одному статусу planned:
нужно соответствующее разрешение. Архитектура и приоритеты — решение пользователя.

Каждый этап подтверждается проверками согласно критериям: для кода — релевантными
тестами, для документации — ссылками, согласованностью и diff. Исторический запуск
тестов отмечается датой и ревизией; его нельзя выдавать за новый прогон.
Персональные данные, секреты, пароли, cookies и дампы не включать в координацию.
Исходный `C:\Projects\AI-Student-Dashboard` не изменять, пути не менять.

## Начало нового чата Astra

Пользователь указывает корень `C:\Projects\MGIMOv`, роль Astra, задачу и режим чтения.
Astra читает четыре coordination-файла и связанные источники, сверяет HEAD/status,
уточняет диапазон аудита по доступным данным. При security review читает
[deanery-security-review](../../.agents/skills/deanery-security-review/SKILL.md).
Команды запуска/миграций из README не являются разрешением их выполнять при аудите.
По умолчанию отчёт остаётся в чате; пользователь передаёт Sol решение и выводы.

## Начало работы Sol или Luna

Sol и Luna начинают задачу с чтения этого workflow и актуальных файлов координации,
проверки Git status/HEAD/diff и выяснения активных задач и владельцев файлов.
Наличие planned-задачи само по себе не разрешает её реализацию. После завершения
назначенный исполнитель обновляет статус и передаёт точное состояние Astra через
существующий review-handoff; замечания аудита остаются в том же процессе.

не менять исходный Dashboard; проверять изменения и записывать результаты;
обновлять статус после этапа; разделять роли Sol/Astra и не допускать параллельной
записи. AGENTS.md сейчас не создаётся. Этот workflow сам по себе не является
автоматически подключённой инструкцией для нового чата — его надо явно прочитать.
