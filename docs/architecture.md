# Архитектура, утверждённая на V1

## Целевая система

Самостоятельный проект с отдельным Git, окружением, конфигурацией и SQLite.
Frontend HTML/CSS/ES modules и FastAPI работают с одного origin. Один экземпляр
сервера и постоянный локальный диск. Бизнес-данные хранятся на сервере.
localStorage не используется для персональных данных. Нет Telegram и старой
синхронизации полных JSON-снимков. Внешние системы университета не подключаются.

Целевые модули: профиль, групповое расписание, личная успеваемость, заявки,
уведомления. Frontend будет разделён на API-клиент, состояние сессии, страницы,
компоненты и независимые вычисления. Backend — маршруты, сервисные правила и SQL
по модулям; дополнительные абстрактные слои не обязательны.

## Целевые этапы (статус реализации уточнён ниже)

V3: Argon2id, серверные сессии, Secure/HttpOnly/SameSite cookies для HTTPS,
CSRF, два вымышленных студента и сотрудник. Публичная регистрация не нужна.
Студент читает свои профиль, оценки, заявки и уведомления, расписание своей группы.
Сотрудник получает операции по факультету: обработка заявок, публикации,
изменение расписания. Автоматического доступа к оценкам нет.

Реляционные сущности: users/sessions; профили; факультеты/программы/группы;
преподаватели/дисциплины/семестры/зачисления; серии и занятия с историей изменений;
оценки/результаты аттестаций; типы/заявки/история; объявления/уведомления.
Профиль получает факультет и программу через группу. Повторения разворачиваются
в занятия в пределах семестра. Время аудита UTC, учебный календарь Europe/Moscow.
Персональный SQL ограничивается владельцем; staff-операции — областью полномочий.
Изменения используют version и 409, история и уведомления записываются атомарно.

V4 — расписание; V5 — успеваемость; V6 — заявки; V7 — уведомления; V8 —
проверка MVP; V9 — согласованные улучшения и сдача. Тесты добавляются по этапам.
Первый HTTPS-стенд планируется после V3. Дополнительные ИИ-функции не выбраны.

## Реальный объём V2

backend/app.py: create_app(Settings), GET /api/health и явный список frontend assets.
backend/config.py: только MGIMOV_DB_PATH, путь ограничен этим проектом.
backend/db.py: существующая SQLite, foreign_keys, read-only чтение и BEGIN IMMEDIATE
для записи. Запуск приложения ничего не создаёт в базе.
backend/migrations: новая 0001_initial с технической меткой приложения и история.
backend/security/passwords.py: примитив Argon2id без маршрутов авторизации.
frontend: стартовая страница, клиент GET JSON, независимые функции дат, тёмная тема.

Исторически V2 health проверял целостность/схему и метку приложения. После V3
hardening public health стал лёгким; полная диагностика вынесена в локальную
команду. Пути и содержимое базы не публикуются (детали ниже).
Доступ к файловой системе через API отсутствует: опубликованы только перечисленные assets.

## Интерфейс

Тёмная тема, фиолетовый и мятный акценты, карточки. Системные шрифты, без логотипа
вуза и внешних CDN. На странице явно указано, что сервис неофициальный.
CSS меняет две колонки на одну на узком экране. Реальная мобильная QA ещё предстоит.

## Реальный объём V3

Backend: auth/service.py — вход, throttling, resolve/CSRF, отзыв; auth/http.py —
exact Host/Origin/transport, Fetch Metadata, bounded JSON; auth/routes.py — строгие
DTO и безопасные ошибки; profiles.py — owner-scoped SQL в read-транзакции.
Новая 0002_identity: users, sessions, auth_rate_limits, faculties, programs,
study_groups, student_profiles, staff_profiles. Профиль студента получает факультет,
программу и курс через группу. V2 SQL не изменялся, default working DB не мигрирована.
Создание users+профилей+справочников seed_demo выполняется одной транзакцией.

API prefix /api/v1: auth/csrf (GET), auth/login (POST), auth/me (GET),
me/profile (GET), auth/logout (POST). Нет выбора чужого user_id или повышения роли.
Staff получает только собственное служебное представление; faculty permissions,
редактор ролей, смена/восстановление пароля и учебные модули пока отсутствуют.
Перед их реализацией потребуются отзыв/ротация сессий при изменении credentials/прав.

Токены session и CSRF — secrets.token_urlsafe(32), в SQLite SHA-256; срок 8 часов,
выход отзывает строку, вход отзывает представленную прежнюю cookie и создаёт новую.
Active пользователя проверяется при каждом защищённом чтении. Logout resolve/CSRF
и revoke выполняются под одной write-транзакцией. Все SQL параметризованы.
Для login используется отдельный preauth CSRF cookie/header и exact Origin.

Frontend: API-клиент, независимый memory-only account-state и DOM adapter account.js.
Generation/AbortController скрывают старые данные и игнорируют поздние ответы.
X-Mgimov-User обозначает ожидаемый аккаунт, прав не выдаёт. BroadcastChannel
передаёт только сигнал invalidation; сервер повторно проверяет owner по cookie.
Скрытая вкладка/pagehide очищает представление; возврат, online и минутная проверка
в видимой вкладке проверяют сессию. Персональные данные в browser storage не пишутся.
После неуспешного logout данные скрыты, выход можно повторить. Отдельные вкладки
одного browser profile разделяют cookie; это не два независимых хранилища сессий.

Два HTTP-клиента в интеграционных тестах обеспечивают независимые студенческие сессии.
Для ручной проверки двух одновременных аккаунтов использовать разные профили браузера.
Браузерная QA V3 на 360 px остаётся неподтверждённой из-за недоступности браузерного runtime.

## V3 hardening (текущее уточнение)

auth/limits.py — атомарные source/pair budgets и bounded verification slots;
успешный вход возвращает только свой счётчик. Общей длительной блокировки логина
или приложения больше нет. Ошибки с одного источника всё ещё могут ограничить
клиентов за общим NAT; распределённую нагрузку решает периметр.
Logout делает дешёвый предварительный отказ, сохраняя повторную транзакционную проверку.
health.py — лёгкая read-only readiness; commands/diagnose.py сохраняет полную
проверку менеджера миграций. commands/cleanup_sessions.py — явная ограниченная очистка,
без удаления действующих сессий и без изменения TTL. Новых таблиц/миграций нет.
IdentityGuard ограничивает абсолютное время чтения body, не только размер.
Frontend сохраняет несданный пароль при фоновом poll и ручном refresh.
[Периметр и служебные команды](deployment-security.md).

## V4 — групповое расписание

Новая 0003_schedule: buildings → rooms (UNIQUE building/number, capacity,
equipment); subjects, teachers; lessons с group_id/subject_id/teacher_id/room_id,
московской календарной date и start/end_minute (0≤start<end≤1440), kind/status/version.
Датированные экземпляры без автоматических серий. Ночные интервалы через полночь
не входят в MVP; их можно представить отдельными дневными экземплярами.
Индексы group/date и room/date/start/end пригодны для будущей проверки занятости.
Cancelled-строки сохраняются для отображения, но не являются занятостью аудитории.

lesson_changes хранит версию, причину, before_date, before/after JSON и UTC timestamp.
Изменение и история атомарны; проверяется ожидаемая версия и внешние ключи.
JSON ограничен историей отображения, основные связи реляционны. Старые SQL не меняются.

GET /api/v1/me/schedule принимает только view=today|week и одиночную date.
Даты строго проверяются, неделя всегда понедельник–воскресенье; today определяет сервер.
Сессия/active/role и группа читаются в одной read-транзакции; SQL ограничен группой
профиля по server user.id. Клиент не выбирает владельца/группу. В ответе нет списков
студентов, паролей и данных сессий. IdentityGuard применяется к новому me-маршруту.

Возвращаются days с текущими занятиями и moved_from-маркерами на прежних датах.
Маркер не создаёт занятие в базе. Несколько переносов сохраняют промежуточные
прежние даты. Полная история «было/стало» отображается текстом, без innerHTML.
Изменения выполняет только доверенный локальный оператор командой change_lesson;
веб-редактор и новые staff permissions не добавлялись. Для будущего HTTP-редактора
необходимо отдельно встроить серверную проверку полномочий перед write-транзакцией.

Frontend: schedule-state (identity binding, даты, загрузка/error/abort), schedule.js
(renderer карточек и DOM adapter). Account lifecycle очищает timetable при logout,
смене/проверке identity; stale response не возвращает прежние данные. Выбор даты
для того же аккаунта сохраняется, новый аккаунт начинает с сегодняшнего дня.
Карточный раздел можно использовать как будущий виджет; чужой UI не копировался.


## V5 — персональная успеваемость

Новая миграция 0004_academics, SQL 0001–0003 не меняются. subjects из V4 переиспользуется.
semesters — именованные календарные интервалы; curriculum_items связывает программу,
дисциплину, семестр, control (exam/credit/graded_credit), required. assessments —
одно обязательное мероприятие плана для группы, scheduled_on/deadline_on nullable,
status scheduled/completed/not_held/cancelled. student_assessments явно назначает
мероприятие конкретному student_profiles.user_id, UNIQUE student/assessment.
assessment_attempts содержит номер попытки, outcome, grade, performed_on и recorded_at UTC.
Повторная попытка не создаёт новое назначение. Существующие дисциплины/группы не хранят оценок.
FK/UNIQUE/CHECK и insert-триггеры проверяют программу/группу, форму контроля, последовательность
попыток и запрет попытки после успеха. UPDATE/DELETE попыток запрещены триггерами.
Это не защита от доверенного администратора с полным доступом к файлу SQLite.

academics/service.py: read_academics открывает read-транзакцию, resolve проверяет живую
сессию, active/role и expected identity. Обе выборки назначений/попыток содержат
sa.student_id=user.id с сервера. Старая история сохраняется после перевода в другую группу.
Данные не выбираются по клиентским ID. Четыре GET me/gradebook, me/exams, me/debts,
me/progress не принимают query; IdentityGuard/no-store/общие безопасные ошибки сохранены.
Staff получает 403, аноним — 401; публичных мутаций нет.

academic_status и summarize задают правила, описанные в [README](../README.md#успеваемость-v5).
Активный семестр определяется календарным интервалом назначений студента. Неоднозначные
пересекающиеся активные семестры дают безопасный 503, а не произвольный выбор.
Неявка — явная неуспешная попытка; неизвестное проведение не равно неявке.
Текущая сессия MVP совпадает с активным семестром; отдельные сессионные окна/планы
пересдач пока не моделируются. Долги прошлых семестров остаются отдельным списком.

seed_academics работает атомарно с отдельной демобазой: два студента, разные программы,
два семестра, экзамен/зачёт/диффзачёт, успех/долг/будущие/непроведённые/невнесённые.
Изменяется только demo-b: новая вымышленная программа, без изменения авторизации.
record_result — локальное добавление валидной попытки с expected-attempts под BEGIN IMMEDIATE;
не HTTP authorization shortcut. Нет редактирования уже успешной оценки/веб-редактора.

Frontend academics-state хранит данные только в памяти, abort/generation/expected user
связаны с account lifecycle; loading/error/clear удаляют старый DOM. academics.js использует
textContent, карточки, progress, раскрываемые семестры и доступные empty/error-состояния.
Новые assets перечислены явно в app.py, новых внешних ресурсов и библиотек нет.


## V6 — электронные заявки

Новая 0005_requests, SQL 0001–0004 не изменяются. student_requests содержит owner FK
на student_profiles, faculty_id (снимок при отправке), type/purpose/message,
status/version/created_at/updated_at, request_key/payload_hash. UNIQUE student/key
защищает повтор POST; индекс owner/created поддерживает квоты и списки.
request_history хранит переход, version, actor_id FK users, actor_role, comment,
UTC created_at; UNIQUE request/version, insert-проверка совпадения текущего статуса,
запрет UPDATE/DELETE истории. request_staff_scopes — явные пары staff_profile/faculty.

requests/service.py: read_requests/authorized_request ограничивают SQL по server user.id
либо EXISTS разрешённого faculty scope. Student ID/actor/role из body не принимаются.
Студент видит только свою заявку; чужой и отсутствующий ID одинаково дают 404.
Сотрудник получает контекст заявителя (имя/группа) только в деталях доступного обращения,
без оценок, credentials или общего доступа к профилям. Новых прав вне заявок нет.

create_request/transition_request делают дешёвый read-only preflight session/CSRF,
затем повторяют live resolve, role/CSRF и проверку владельца/scope под BEGIN IMMEDIATE.
Текущий статус и история меняются в одной транзакции; ошибка истории откатывает статус.
Version конфликт даёт 409. TRANSITIONS: submitted→processing→approved|rejected для
сотрудника; submitted→cancelled для владельца. Терминальные переходы запрещены.
Начальная отправка тоже фиксируется в истории. Авторы решений определяются сервером.
Имена автора отображаются из профилей, неизменный actor_id и роль события остаются в БД.

Создание ограничено 5/600s и 20/86400s на владельца, включая отменённые. В одной
транзакции проверяются owner/key/payload_hash, квота и вставка. Идемпотентный повтор
не расходует квоту; иной payload с тем же key — 409. Роли/request_key не заменяют авторизацию.
HTTP тела/DTO ограничены по длине, extra=forbid; SQL параметризован, свободный текст
выводится textContent/pre-wrap. Ошибки безопасные, ответы no-store.

Новые routes /api/v1/me/requests и /api/v1/staff/requests явно отделены. IdentityGuard
и общий обработчик validation расширены на staff prefix: exact Origin/Host/transport,
Fetch Metadata, CSRF duplicates, JSON/body limit/deadline/no-store сохранены.
CSRF каждой mutation привязан к живой серверной сессии, не только cookie/header equality.

requests-state: один in-flight, технический ключ восстановления в sessionStorage, AbortController/
epoch/expected identity, пагинация. requests.js: форма студента, карточки/история,
доступные действия и комментарий сотрудника. Account-state сообщает вид проверки:
при refresh представление скрывается, несданная форма сохраняется только для того
же подтверждённого аккаунта; при смене/ошибке/выходе данные и форма очищаются.
Комментарий сотрудника хранится в памяти отдельно по owner/request, переживает
suspend/refresh/error/409 и очищается после подтверждённого действия/logout/смены
пользователя. При terminal conflict доступен только для копирования, без auto retry.
Assets перечислены явно, зависимости не добавлены. Файлов/печатей/подписей/официальных
документов, needs_info и редактирования обращений после отправки нет.


### AUD-01 / AUD-02 — 5 ноября 2026

request-operation.js хранит только {v,key,type,tag,expiresAt} в sessionStorage вкладки.
tag=SHA-256(domain + user.id + random key), случайный для каждой операции; сам UUID
пользователя и стабильный идентификатор аккаунта не записываются. Это техническая
привязка, не авторизация или секрет сессии. Срок 24 часа. Проверка владельца выполняется
после server-confirmed identity; чужой маркер удаляется. Перед POST save проверяется
чтением, недоступное хранилище блокирует отправку. Personal form data и fingerprints
содержимого не сохраняются. При reload ключ восстанавливается, текст вводится заново.
Смена типа неподтверждённой операции требует явной новой отправки; изменённый текст
с тем же ключом проверяет неизменённый backend payload_hash (409 при несовпадении).
Успех очищает маркер; logout удаляет, pagehide сохраняет только технические метаданные.
Закрытие/восстановление вкладки — поведение sessionStorage браузера, не гарантия хранения.
Новые endpoints/миграции/серверная модель идемпотентности не добавлялись; в app.py только
asset нового ES module. Сервер по-прежнему является источником истины.
