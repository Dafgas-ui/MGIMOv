# Требования к публичному периметру V3

Статус: требования к будущему размещению, **не проверенная конфигурация хостинга**.
В этом задании приложение не публиковалось. Применять и проверять на отдельном
стенде по разрешению пользователя. Единственный процесс приложения, одна SQLite
на постоянном диске; не включать несколько workers, полагаясь на process-local лимиты.

| Требование | Критерий будущей проверки |
|---|---|
| Настоящий HTTPS | Действительный сертификат, корректная цепочка и HTTPS origin; Secure/__Host cookies. Никаких обходов предупреждений браузера |
| Доверенный reverse proxy | Backend слушает loopback/закрытый socket, прямого публичного доступа нет; Host допускается только для согласованного origin |
| Прокси-заголовки | Proxy перезаписывает forwarded headers; приложение доверяет только его адресу. Проверить поддельные X-Forwarded-For/Proto от клиента и прямой запрос. Не доверять wildcard-источникам |
| Приём headers/body | Proxy ограничивает чтение заголовков и тела целиком, не только keep-alive. Пример начальной цели: headers <=10 секунд, identity body <=10 секунд; проверить единичный slow request |
| Размер | Identity JSON <=8192 байт; проверить как Content-Length, так и chunked. Не полагаться только на заявленную длину |
| Соединения/конкурентность | Задать и измерить per-source и общий предел соединений, backlog и concurrency Uvicorn; отсутствие бесконечной очереди. Проверить несколько легитимных клиентов за NAT, а не выбирать порог вслепую |
| Частота анонимных запросов | Отдельные правила для login/bootstrap/health/static, burst и общий предел нагрузки. Не блокировать аккаунт только по чужим запросам. Проверить распределённые источники и общий NAT |
| Логи | Не писать cookies, password, CSRF, тела login и полные приватные ответы. Ограничить доступ, срок хранения, ротацию; проверить редактирование тестовых секретов |
| Backup/restore | Закрытые копии вне основного диска, согласованные retention/частота; восстановить отдельную копию, проверить диагноз и вход. Доступ к SQLite/backup по HTTP закрыт |
| Доступность/перезапуск | Проверить лёгкий health 200/503, запуск после перезагрузки с постоянным диском, отсутствие автоматического seed/reset и ложного восстановления сессий |

Начальные значения — цели для стенда, не доказанная защита. Реальные лимиты соединений
и частоты выбрать по небольшому согласованному измерению памяти/CPU и NAT-сценариям.
При HTTPS termination origin и ASGI scheme должны соответствовать конфигурации;
разрешать forwarded headers только от точно указанного proxy, не от Интернета.

## Что ограничивает само приложение

IdentityGuard ограничивает тело 8192 байтами и абсолютными 10 секундами от начала
чтения ASGI body. Отдельные chunks не продлевают deadline. Это не timeout заголовков,
не ограничитель количества открытых соединений и не замена proxy.
LoginLimits разрешает не более двух проверок пароля одновременно и одной проверки
одного логина в одном процессе; Argon2 semaphore также сохранён. Переполнение даёт
503, а исчерпанный source/pair budget — 429 с Retry-After 60.

Ограничение запросов по источнику принципиально зависит от доверенной идентичности
источника. Без proxy request.client должен быть настоящим socket peer; behind proxy
нельзя считать всех пользователей одним адресом proxy или доверять чужому forwarded header.

## Диагностика и обслуживание

Публичный GET /api/health — read-only connection с коротким ожиданием, метка
приложения, ожидаемые migration ids/checksums и доступность основных таблиц.
200/503 и JSON status сохранены. Полная целостность и точное совпадение схемы
этим endpoint больше не удостоверяются; возможны повреждения, которые лёгкий SELECT
не заметит. Полная проверка остаётся локальной командой (не endpoint):

```powershell
& .\.venv\Scripts\python.exe -B -m backend.commands.diagnose --db .tmp/demo-v3.sqlite3
```

Команда только читает SQLite, проверяет integrity/FK/schema/checksums, печатает
общий результат без данных и возвращает 0 либо 1. Выполнять в согласованное время;
она может быть ресурсоёмкой, несмотря на отсутствие записи.

Ограниченная очистка: только явный запуск на согласованной базе, по умолчанию
не более 100 сессий (max 500); истёкшие или отозванные не менее суток назад.
Живые сессии и недавно отозванные с ещё действующим TTL сохраняются. TTL не меняется.

```powershell
& .\.venv\Scripts\python.exe -B -m backend.commands.cleanup_sessions --db .tmp/demo-v3.sqlite3 --limit 100 --confirm-cleanup
```

Нет нового scheduler/service и нет автоматического запуска на рабочей базе.
Число удалений ограничено, но без новых индексов поиск старых строк при росте
таблицы может дорожать; оценить индексы/retention перед большой нагрузкой.
Старые auth counters очищаются не более чем по 20 строк в уже разрешённой
write-транзакции резервирования; повторные 429 ничего не очищают и не пишут.
